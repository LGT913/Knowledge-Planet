## 一、MySQL

### 1.1 索引

#### B+Tree 为什么适合做索引

B+Tree 是 B-Tree 的变体，核心设计取舍在于"磁盘 I/O 次数"和"范围查询效率"。

**为什么不用 B-Tree：**

B-Tree 的每个节点既存索引也存数据，导致单个节点能容纳的索引键数量减少。同样数据量下，B-Tree 的树更高，磁盘 I/O 次数更多。而且 B-Tree 的叶子节点之间没有指针连接，范围查询需要回到根节点重新遍历。

**为什么不用 Hash 索引：** Hash 索引虽然等值查询 O(1)，但不支持范围查询（`>`、`<`、`BETWEEN`）、不支持排序（`ORDER BY`）、不支持最左前缀匹配。数据库场景中范围查询和排序极其频繁，Hash 索引适用面太窄。

**B+Tree 的关键优势：**

- 非叶子节点只存储索引键 + 指针，不存数据，一个节点能容纳更多键，树更矮。InnoDB 页大小默认 16KB，三阶 B+Tree 可支撑约 2000 万行数据。
- 数据全部存放在叶子节点，且叶子节点通过双向链表连接，范围查询只需定位起点后顺序扫描链表即可。

```sql
-- 查看索引树高度（通过 information_schema 间接估算）
SELECT 
  b.table_name,
  b.index_name,
  b.stat_value AS leaf_pages,
  ROUND(b.stat_value * 16384 / 1024 / 1024, 2) AS leaf_size_mb
FROM information_schema.innodb_buffer_page b
WHERE b.index_name = 'PRIMARY';
```

#### 聚簇索引 vs 非聚簇索引（回表、覆盖索引）

**聚簇索引**：索引和数据行存储在同一棵 B+Tree 中，叶子节点就是数据页本身。InnoDB 的主键索引就是聚簇索引，一张表只能有一个聚簇索引。

**非聚簇索引（二级索引）**：叶子节点存储的是索引键值 + 主键值，而非完整数据行。通过二级索引查到主键后，还需要回聚簇索引中查找完整数据，这个过程叫**回表**。

```sql
-- 假设有表：user(id PK, name, age, city)，在 city 上建了二级索引 idx_city
-- 下面这条查询需要回表：
SELECT * FROM user WHERE city = '北京';
-- 1. 先走 idx_city 找到主键 id
-- 2. 再回聚簇索引查完整行数据

-- 覆盖索引：查询字段全在索引中，无需回表
SELECT id, city FROM user WHERE city = '北京';
-- Extra 列显示 Using index，表示走了覆盖索引
```

**为什么 InnoDB 选择聚簇索引存储**：聚簇索引将索引和数据合并在一棵 B+Tree，主键查询只需一次 I/O 即可拿到完整行数据。非聚簇索引虽然多一次回表，但因为主键值在索引中已排序，回表操作是主键查找，效率很高。

#### 联合索引最左前缀原则

联合索引 `(a, b, c)` 在 B+Tree 中按 a→b→c 的顺序排列。最左前缀原则要求查询条件必须从联合索引的最左列开始使用，否则无法走索引。

```sql
-- 联合索引 idx_abc(a, b, c)

-- 能走索引的情况：
SELECT * FROM t WHERE a = 1;                    -- 使用 a
SELECT * FROM t WHERE a = 1 AND b = 2;          -- 使用 a, b
SELECT * FROM t WHERE a = 1 AND b = 2 AND c = 3; -- 使用 a, b, c
SELECT * FROM t WHERE a = 1 AND c = 3;          -- 只能用到 a（索引下推前只走 a）

-- 不能走索引的情况：
SELECT * FROM t WHERE b = 2;                    -- 缺少最左列 a
SELECT * FROM t WHERE b = 2 AND c = 3;          -- 缺少最左列 a
```

**为什么这样设计**：B+Tree 的排序规则是先按 a 排序，a 相同再按 b 排序，b 相同再按 c 排序。如果跳过 a 直接查 b，B+Tree 中的数据在 b 列上并不全局有序，无法利用二分查找。

#### 索引下推 ICP（Index Condition Pushdown）

MySQL 5.6 引入的优化。在没有 ICP 时，存储引擎根据联合索引取出满足最左前缀的记录后，全部回表交给 Server 层过滤其余条件。ICP 将部分 WHERE 条件"下推"到引擎层，在回表前先过滤，减少回表次数。

```sql
-- 联合索引 idx_name_age(name, age)
SELECT * FROM user WHERE name LIKE '张%' AND age > 18;

-- 无 ICP：引擎层按 name 前缀匹配取出所有"张X"记录，全部回表，Server层再过滤 age>18
-- 有 ICP：引擎层取出"张X"后，先用 age>18 过滤，只对满足条件的记录回表
-- Explain 的 Extra 列显示 "Using index condition"
```

#### 面试题

**Q：为什么 MySQL 用 B+Tree 而不是 B-Tree？**

A：B+Tree 非叶子节点只存索引不存数据，单页能容纳更多键，树更矮，磁盘 I/O 更少；叶子节点通过双向链表连接，范围查询和排序效率远高于 B-Tree 需要中序遍历。B-Tree 每个节点都存数据，导致树更高，且叶子节点无链表连接，范围查询需要多次回到根节点。

**Q：什么是覆盖索引？什么是回表？**

A：覆盖索引指查询所需的所有字段都包含在索引中，引擎层直接从索引返回数据，无需回聚簇索引查完整行，Extra 显示 `Using index`。回表是指通过二级索引拿到主键值后，还要去聚簇索引中查找完整数据行的过程。覆盖索引避免了回表，减少磁盘 I/O，应尽量让查询只返回索引覆盖的列。

**Q：联合索引 (a,b,c)，哪些查询能走索引？**

A：能走索引：`a=1`、`a=1 AND b=2`、`a=1 AND b=2 AND c=3`、`a=1 AND c=3`（仅 a 部分走索引，ICP 下推后 b 仍可参与过滤但不算走索引范围扫描）。不能走索引：`b=2`、`b=2 AND c=3`（缺少最左列 a）、`a>1 AND b=2`（a 走范围扫描后 b 无法有序，无法利用索引）。

### 1.2 事务隔离级别

#### 四种隔离级别 + 对应问题

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|---------|------|-----------|------|------|
| READ UNCOMMITTED (RU) | 可能 | 可能 | 可能 | 能读到未提交的数据 |
| READ COMMITTED (RC) | 避免 | 可能 | 可能 | 只能读到已提交的数据 |
| REPEATABLE READ (RR) | 避免 | 避免 | 可能 | 同一事务内多次读同一行结果一致 |
| SERIALIZABLE | 避免 | 避免 | 避免 | 串行化执行，完全隔离 |

- **脏读**：事务 A 读到了事务 B 未提交的数据，B 回滚后 A 读到的是无效数据。
- **不可重复读**：事务 A 两次读同一行，中间事务 B 修改了该行并提交，A 两次读到不同值。
- **幻读**：事务 A 两次执行同一范围查询，中间事务 B 新增/删除了行，A 第二次多/少了行。

#### MySQL 默认 RR，为什么不是 RC

MySQL InnoDB 默认隔离级别是 RR（可重复读），而 Oracle、PostgreSQL 等数据库默认 RC。MySQL 选择 RR 的原因与主从复制有关：

早期 MySQL 的主从复制基于 `binlog_format=statement`，主库按语句顺序写入 binlog，从库按顺序回放语句。在 RC 隔离级别下，事务的执行顺序可能影响结果——例如先 UPDATE 后 SELECT，与先 SELECT 后 UPDATE 的结果不同，导致主从数据不一致。RR 级别下 InnoDB 通过 Next-Key Lock 锁住范围，保证同一事务内相同查询结果一致，使 statement 格式 binlog 的复制是安全的。

不过现代 MySQL 也支持 `binlog_format=row`，基于行的复制不依赖语句顺序，因此很多互联网公司（如阿里）将隔离级别改为 RC 以提升并发性能。

#### 面试题

**Q：MySQL 的四种事务隔离级别？**

A：READ UNCOMMITTED 可能脏读；READ COMMITTED 避免脏读但可能不可重复读；REPEATABLE READ 避免脏读和不可重复读，InnoDB 在 RR 级别通过 Next-Key Lock 也能避免大部分幻读；SERIALIZABLE 完全串行化避免所有问题但性能最差。MySQL 默认 RR，原因是配合 statement 格式 binlog 保证主从复制一致性。实际生产中很多公司改为 RC 提升并发度，配合 row 格式 binlog。

### 1.3 MVCC

#### undo log 版本链

MVCC（多版本并发控制）的核心思路：读操作不阻塞写操作，写操作也不阻塞读操作。每行数据维护多个历史版本，读操作根据自己的可见性规则选择合适的版本。

InnoDB 每行数据隐藏了两个字段：`trx_id`（最近修改该行的事务ID）和 `roll_pointer`（指向 undo log 中该行的上一个版本）。每次更新一行，旧值被写入 undo log，`roll_pointer` 指向旧版本，多个版本通过 `roll_pointer` 串联成一条版本链。

```
当前行数据 (trx_id=300) 
  └─ roll_pointer → undo log v2 (trx_id=200)
                      └─ roll_pointer → undo log v1 (trx_id=100)
```

#### ReadView 生成时机（RC vs RR 的区别）

ReadView 是事务在读取数据时生成的"快照"，包含当前活跃（未提交）事务的 ID 列表。通过 ReadView 判断某个版本对当前事务是否可见：

- `min_trx_id`：ReadView 中活跃事务的最小 ID
- `max_trx_id`：下一个将被分配的事务 ID
- 可见性判断规则：
  - `trx_id < min_trx_id`：事务已提交，可见
  - `trx_id >= max_trx_id`：事务在 ReadView 生成后才启动，不可见
  - `min_trx_id <= trx_id < max_trx_id`：若 trx_id 在活跃列表中则不可见，否则可见

**RC 和 RR 的关键区别：**

| | ReadView 生成时机 | 效果 |
|---|---|---|
| RC | 每条 SELECT 都生成新的 ReadView | 每次读都能看到最新已提交的数据 → 不可重复读 |
| RR | 事务内第一条 SELECT 时生成，后续复用 | 事务内多次读看到的数据一致 → 可重复读 |

#### 面试题

**Q：MVCC 是怎么实现的？**

A：MVCC 通过 undo log 版本链 + ReadView 实现。每行数据有隐藏的 trx_id 和 roll_pointer，更新时旧值写入 undo log，通过 roll_pointer 串联成版本链。读操作生成 ReadView，包含当前活跃事务列表，按照 trx_id 与活跃列表的比较规则判断哪个版本可见。RC 隔离级别每次 SELECT 生成新 ReadView，所以能看到其他事务最新提交的修改（不可重复读）；RR 隔离级别只在第一次 SELECT 时生成 ReadView，后续复用，所以整个事务内读到的数据一致。MVCC 只在快照读（普通 SELECT）生效，当前读（SELECT FOR UPDATE、UPDATE、DELETE）不走 MVCC 而是加锁。

### 1.4 锁

#### 行锁、间隙锁、临键锁

InnoDB 行锁是加在索引上的，不是加在数据行上的。如果查询没有走索引，会导致锁升级为表锁。

| 锁类型 | 作用范围 | 说明 |
|--------|---------|------|
| Record Lock（记录锁） | 单行 | 锁住索引上的一条记录 |
| Gap Lock（间隙锁） | 开区间 (a, b) | 锁住两个记录之间的间隙，防止插入，解决幻读 |
| Next-Key Lock（临键锁） | 前闭后开 (a, b] | Record Lock + Gap Lock，锁住记录及其左侧间隙 |

```sql
-- 表 t 有数据：id=10, id=20, id=30（id 是主键）

-- 事务 A 在 RR 级别下执行：
SELECT * FROM t WHERE id BETWEEN 15 AND 25 FOR UPDATE;
-- 会加 Next-Key Lock：(10, 20] 和 (20, 30)
-- 事务 B 执行 INSERT INTO t VALUES (16); 会被阻塞，因为 16 在 (10,20] 间隙内
```

**唯一索引等值查询优化**：当等值查询命中唯一索引时，Next-Key Lock 会退化为 Record Lock，不会锁住间隙，因为唯一索引已保证不会有重复值插入。

#### 意向锁、MDL（元数据锁）

**意向锁（IS / IX）**是表级锁，作用是让"表锁"和"行锁"之间快速判断是否冲突。事务在加行级共享锁前先加表级 IS 锁，加行级排他锁前先加表级 IX 锁。这样当另一个事务要加表锁时，只需检查意向锁，不用逐行扫描。

**MDL（Metadata Lock）元数据锁**：MySQL 5.5 引入，保护表结构不被并发修改。事务访问表时自动加 MDL 读锁，执行 DDL（ALTER TABLE 等）时加 MDL 写锁。DDL 要等所有持有 MDL 读锁的事务释放，所以线上大表加字段容易导致阻塞甚至锁等待雪崩。

#### 面试题

**Q：MySQL 有哪些锁？间隙锁解决什么问题？**

A：按粒度分：表锁（意向锁 IS/IX、MDL 元数据锁、AUTO-INC 锁）和行锁（Record Lock 记录锁、Gap Lock 间隙锁、Next-Key Lock 临键锁）。按模式分：共享锁（S，读锁）和排他锁（X，写锁）。间隙锁锁住索引记录之间的间隙，防止其他事务在间隙中插入新行，从而解决 RR 隔离级别下的幻读问题。Next-Key Lock 是 InnoDB 在 RR 级别下默认的行锁类型，等于 Record Lock + Gap Lock，锁住记录及其左侧间隙。需要注意的是间隙锁只在 RR 级别存在，RC 级别没有间隙锁。

### 1.5 Explain 分析

#### type 字段等级

`type` 列表示 MySQL 如何查找数据，从好到差：

| 等级 | 说明 | 典型场景 |
|------|------|---------|
| system | 表只有一行 | 系统表 |
| const | 通过主键或唯一索引等值查询 | `WHERE id = 1` |
| eq_ref | 联合查询中使用主键/唯一索引 | JOIN 被驱动表用主键关联 |
| ref | 通过普通索引等值查询 | `WHERE name = '张三'` |
| range | 索引范围扫描 | `WHERE id BETWEEN 1 AND 100` |
| index | 全索引扫描 | 查询字段全在索引中但无过滤条件 |
| ALL | 全表扫描 | 无索引或索引失效 |

**优化目标**：至少达到 range 级别，最好达到 ref 级别。

#### Extra 字段含义

| Extra 值 | 含义 | 是否需要优化 |
|---------|------|-------------|
| Using index | 覆盖索引，无需回表 | 理想状态 |
| Using where | Server 层过滤 | 检查是否可优化索引 |
| Using index condition | 索引下推 ICP | 已优化 |
| Using filesort | 额外排序 | 需优化，检查 ORDER BY 字段是否有索引 |
| Using temporary | 使用临时表 | 需优化，常见于 GROUP BY、DISTINCT |
| Using join buffer | Join 无索引走 Block Nested Loop | 需加索引 |

#### 面试题

**Q：如何分析一条 SQL 的执行计划？**

A：用 `EXPLAIN SELECT ...` 查看。重点看四个字段：`type` 表示访问类型，从 const 到 ALL，至少要 range；`key` 显示实际使用的索引，如果为 NULL 说明没走索引；`rows` 是预估扫描行数，越小越好；`Extra` 中 `Using filesort` 和 `Using temporary` 是危险信号需要优化，`Using index` 表示覆盖索引是理想状态。还会看 `possible_keys`（可能用的索引）和 `key` 对比，如果 possible_keys 有值但 key 为 NULL，说明优化器选错了，可能需要 `force index`。

```sql
EXPLAIN SELECT * FROM user WHERE city = '北京' ORDER BY age;

-- 理想结果示例：
-- type: ref
-- key: idx_city_age
-- rows: 1200
-- Extra: Using index condition
```

### 1.6 慢查询优化

#### 索引失效场景

```sql
-- 1. 对索引字段做函数运算
SELECT * FROM t WHERE DATE(create_time) = '2026-01-01';  -- 失效
-- 优化：改为范围查询
SELECT * FROM t WHERE create_time >= '2026-01-01' AND create_time < '2026-01-02';

-- 2. 隐式类型转换
SELECT * FROM t WHERE phone = 13800138000;  -- phone 是 varchar，传入数字导致失效
-- 优化：加引号
SELECT * FROM t WHERE phone = '13800138000';

-- 3. LIKE 前缀通配符
SELECT * FROM t WHERE name LIKE '%张';  -- 失效
SELECT * FROM t WHERE name LIKE '张%';  -- 能走索引

-- 4. OR 连接（一侧无索引则全部失效）
SELECT * FROM t WHERE a = 1 OR b = 2;  -- 若 b 无索引则全表扫描

-- 5. != / NOT IN / NOT EXISTS
SELECT * FROM t WHERE status != 1;  -- 通常失效，优化器选择全表扫描
-- 优化：改写为 IN
SELECT * FROM t WHERE status IN (0, 2, 3);

-- 6. 联合索引违反最左前缀
SELECT * FROM t WHERE b = 2;  -- idx(a,b) 失效
```

#### force index

当优化器因为统计信息不准而选择错误索引时，可以用 `FORCE INDEX` 强制指定索引：

```sql
-- 优化器可能选择全表扫描而不是走索引
SELECT * FROM order FORCE INDEX (idx_user_id) WHERE user_id = 10086;
```

#### 面试题

**Q：索引什么时候会失效？**

A：常见失效场景有六类。一是对索引字段做函数运算或运算（`WHERE age + 1 = 20`），索引列被破坏无法走索引。二是隐式类型转换，如 varchar 列传入数字。三是 LIKE 以 `%` 开头。四是 OR 连接的条件中有一侧没有索引，会导致整个查询放弃索引。五是 `!=`、`NOT IN`、`NOT EXISTS` 通常走全表扫描。六是联合索引违反最左前缀原则。此外如果优化器评估走索引比全表扫描代价更大（比如筛选结果占表的大比例），也会放弃索引走全表扫描，这时可用 `FORCE INDEX` 指定索引。

### 1.7 主从复制

#### binlog 格式

| 格式 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| statement | 记录 SQL 语句 | 日志量小 | 函数（NOW()、UUID()）可能导致主从不一致 |
| row | 记录每行数据的变更 | 数据一致性好 | 日志量大（尤其批量操作） |
| mixed | 自动选择 statement 或 row | 兼顾两者 | 逻辑复杂 |

#### 异步复制 vs 半同步复制

- **异步复制**：主库提交事务后不等从库确认，直接返回客户端。性能高但主库宕机可能丢失未同步的事务。
- **半同步复制**：主库提交事务后至少等待一个从库确认收到 binlog 才返回客户端。降低数据丢失风险，增加少量延迟。

#### GTID

GTID（Global Transaction Identifier）格式为 `server_uuid:transaction_id`，每个事务全局唯一标识。相比传统的基于 binlog 文件名 + position 的复制，GTID 让从库自动知道需要从哪个事务开始复制，简化了主从切换和故障恢复。

```sql
-- 查看主库状态（传统方式）
SHOW MASTER STATUS;
-- 查看从库状态
SHOW SLAVE STATUS\G

-- GTID 方式下配置从库
CHANGE MASTER TO 
  MASTER_HOST='192.168.1.100',
  MASTER_AUTO_POSITION=1;  -- 自动定位 GTID
```

#### 面试题

**Q：MySQL 主从复制的原理？**

A：主从复制基于 binlog 实现，分三个步骤：主库执行事务后将变更写入 binlog；从库的 IO 线程连接主库，请求读取 binlog，主库的 Dump 线程将 binlog 发送给从库，从库 IO 线程将日志写入 relay log（中继日志）；从库的 SQL 线程读取 relay log 回放事务，实现数据同步。binlog 有三种格式：statement 记录 SQL 语句但函数可能导致不一致；row 记录每行变更一致性最好但日志量大；mixed 自动选择。复制方式有异步复制（性能高可能丢数据）和半同步复制（至少等一个从库 ACK）。现代 MySQL 推荐用 GTID 代替传统的 file+position 方式，自动定位复制位点，简化故障切换。

### 1.8 分库分表

#### 垂直拆分 vs 水平拆分

| | 垂直拆分 | 水平拆分 |
|---|---------|---------|
| 拆分维度 | 按业务/字段拆 | 按数据行拆 |
| 典型场景 | 大字段拆到扩展表；不同业务拆到不同库 | 单表数据量过大（千万级以上） |
| 特点 | 表结构变化，数据量不变 | 表结构不变，数据分散到多表/多库 |
| 难点 | 跨库 JOIN、分布式事务 | 路由、跨库分页、聚合查询 |

#### 分片策略

- **hash 分片**：对分片键取模，数据均匀分布，但扩容需要 rehash 迁移大量数据。
- **range 分片**：按范围（如按时间、ID 段）分片，适合范围查询，但容易热点。
- **一致性 hash**：新增节点只影响相邻区间的数据，减少迁移量，但实现复杂。

```java
// hash 分片示例
int shardCount = 16;
int shardIndex = userId.hashCode() % shardCount;
String table = "order_" + shardIndex;
```

#### ShardingSphere

Apache ShardingSphere 提供两种模式：

- **ShardingSphere-JDBC**：以 jar 包形式嵌入应用，在 JDBC 层做 SQL 解析、路由、改写，轻量级无额外进程，适合 Java 技术栈。
- **ShardingSphere-Proxy**：独立部署的数据库代理，应用连接 Proxy 像连接真实数据库一样，对语言透明，但增加一层网络开销。

#### 面试题

**Q：什么时候需要分库分表？**

A：一般经验值是单表数据量超过 500 万~1000 万行，或单表数据文件超过 10GB，B+Tree 层级增加导致查询性能下降。分库分表解决的是存储容量和单机性能瓶颈。垂直拆分先做，把大字段拆到扩展表、把不同业务拆到不同库；水平拆分后做，把同一张表的数据分散到多个表或多个库。难点在于跨库 JOIN、分布式事务、全局唯一 ID 和分页查询（如"查看第3页"需要查所有分片再合并）。中间件用 ShardingSphere，分片策略常用一致性 hash 兼顾均匀分布和扩容友好。但分库分表是最后手段，优先考虑优化索引、读写分离、数据归档等方案。

## 二、Redis

### 2.1 数据结构

#### 五种基本类型及底层实现

| 类型 | 底层结构 | 典型场景 |
|------|---------|---------|
| String | SDS（Simple Dynamic String） | 缓存、计数器、分布式锁 |
| List | quicklist（双向链表 + listpack 节点） | 消息队列、最新列表 |
| Hash | listpack（小） / hashtable（大） | 对象存储（用户信息） |
| Set | intset（纯整数） / hashtable | 去重、标签、共同好友 |
| ZSet | listpack（小） / skiplist + dict（大） | 排行榜、延迟队列 |

**String 底层 SDS**：相比 C 字符串，SDS 记录了 len 和 free 长度，获取长度 O(1)，二进制安全（不依赖 \0 判断结尾），空间预分配和惰性释放减少内存重分配次数。

**ZSet 底层 skiplist + dict**：ZSet 同时需要排序（按 score）和查找（按 member）。skiplist（跳表）支持按 score 范围查询 O(logN)，dict 支持 O(1) 按 member 查 score。两者组合让 ZSet 既能范围查询又能快速点查。

```redis
# ZSet 排行榜示例
ZADD ranking 100 alice 90 bob 85 charlie
# 按 score 降序取前3名
ZREVRANGE ranking 0 2 WITHSCORES
# 查看 alice 的排名
ZREVRANK ranking alice
```

#### HyperLogLog、Bitmap

- **HyperLogLog**：用于基数统计（UV 统计），12KB 内存可统计 2^64 个不同元素，误差率约 0.81%。不存储原始数据，不能取出具体值。
- **Bitmap**：位图，操作 String 的位，适合状态标记。1 亿用户签到只需约 12MB。

```redis
# HyperLogLog 统计 UV
PFADD uv:20260101 user1 user2 user3
PFCOUNT uv:20260101  # 返回基数

# Bitmap 签到
SETBIT sign:202601:uid001 0 1   # 1月1日签到
SETBIT sign:202601:uid001 1 1   # 1月2日签到
BITCOUNT sign:202601:uid001      # 统计签到天数
```

#### 面试题

**Q：Redis 有哪些数据类型？ZSet 底层是什么？**

A：五种基本类型：String（SDS）、List（quicklist）、Hash（listpack/hashtable）、Set（intset/hashtable）、ZSet（listpack/skiplist+dict）。扩展类型有 HyperLogLog（基数统计）、Bitmap（位图）、GeoHash（地理位置）、Stream（消息流）。ZSet 底层在元素较少时用 listpack（紧凑连续内存），元素较多时切换为 skiplist + dict 的组合结构：skiplist 按 score 有序支持范围查询，dict 按 member 索引支持 O(1) 查找。切换条件是元素数超过 128 或单个元素长度超过 64 字节（可通过 `zset-max-listpack-entries` 和 `zset-max-listpack-value` 配置）。

### 2.2 持久化

#### RDB vs AOF

| | RDB | AOF |
|---|-----|-----|
| 原理 | 全量快照，fork 子进程生成二进制 dump 文件 | 追加写日志，记录每条写命令 |
| 触发方式 | save（阻塞）/ bgsave（后台）/ 自动触发 | always / everysec / no |
| 恢复速度 | 快（直接加载二进制文件） | 慢（需重放命令） |
| 数据安全 | 两次 RDB 之间的数据可能丢失 | everysec 最多丢 1 秒 |
| 文件大小 | 小（压缩二进制） | 大（文本命令，需 rewrite 压缩） |

**RDB 为什么用 fork 子进程**：Redis 是单线程处理命令的，生成快照时不能阻塞主线程。fork 后子进程共享主进程的内存页（写时复制 COW），子进程遍历内存生成快照，主进程继续处理请求。如果主进程修改了某页数据，操作系统才复制那一页。

**AOF 的三种刷盘策略**：`always`（每条命令刷盘，最安全但性能最差）、`everysec`（每秒刷盘，性能和安全折中，默认）、`no`（由操作系统决定，性能最好但可能丢数据）。

#### 混合持久化（RDB + AOF）

Redis 4.0 引入混合持久化。AOF rewrite 时不再生成纯命令日志，而是先写 RDB 格式的全量数据，再追加 AOF 增量命令。恢复时先加载 RDB 快速恢复大部分数据，再重放 AOF 末尾的少量增量命令，兼顾恢复速度和数据安全。

```
AOF 文件结构（混合持久化）:
[RDB binary data] [AOF command 1] [AOF command 2] ...
```

#### 面试题

**Q：RDB 和 AOF 的区别？怎么选？**

A：RDB 是全量快照，fork 子进程生成二进制文件，恢复快但两次快照间可能丢数据；AOF 是追加写日志，记录每条写命令，数据安全但恢复慢。选择上：如果对数据安全性要求不高（如纯缓存），用 RDB 即可。如果不能丢数据，用 AOF + everysec，最多丢 1 秒。Redis 4.0 后推荐混合持久化，AOF 文件以 RDB 全量开头 + AOF 增量结尾，恢复时先快速加载 RDB 再重放少量 AOF 命令，兼顾速度和安全。生产中通常同时开启 RDB（用于冷备和快速重启）和 AOF（用于数据安全）。

### 2.3 过期策略

#### 定期删除 + 惰性删除

Redis 对带过期时间的 key 采用两种策略配合：

- **定期删除**：Redis 每 100ms 随机抽取部分设置了过期时间的 key 检查，删除已过期的。如果过期 key 比例超过 25%，继续抽样删除，循环直到比例降低。这是主动清理。
- **惰性删除**：不主动检查，而是在 key 被访问时检查是否过期，过期则删除返回 nil。这是被动清理。

两种策略互补：定期删除清理大部分过期 key，惰性删除兜底处理定期删除遗漏的 key。如果大量过期 key 既没被定期删除命中，也没被访问触发惰性删除，内存会持续增长，这时由淘汰策略兜底。

#### 面试题

**Q：Redis 的过期策略是什么？**

A：Redis 用定期删除 + 惰性删除的组合策略。定期删除是每隔 100ms 随机抽查一批带过期的 key，删除已过期的，如果过期比例超 25% 就继续抽样。惰性删除是访问 key 时才检查是否过期，过期就删掉。两种策略互补——定期删除处理大量过期的 key，惰性删除兜底处理定期删除没抽到的。如果两种策略都没及时清理，内存仍持续增长，就由内存淘汰策略兜底，当内存达到 `maxmemory` 限制时触发淘汰。

---

### 2.4 淘汰策略

#### 8 种淘汰策略

当 Redis 内存使用达到 `maxmemory` 限制时，根据淘汰策略选择 key 删除以腾出空间：

| 策略 | 淘汰范围 | 算法 | 适用场景 |
|------|---------|------|---------|
| noeviction | 不淘汰 | — | 内存满时拒绝写入，适合不能丢数据的场景 |
| allkeys-lru | 所有 key | LRU | 缓存场景，淘汰最久未访问的 |
| allkeys-lfu | 所有 key | LFU | 缓存场景，淘汰访问频率最低的 |
| allkeys-random | 所有 key | 随机 | 无明显热点时 |
| volatile-lru | 设了过期的 key | LRU | 混合持久化和缓存时 |
| volatile-lfu | 设了过期的 key | LFU | 同上 |
| volatile-ttl | 设了过期的 key | 优先淘汰 TTL 短的 | 优先淘汰快过期的 |
| volatile-random | 设了过期的 key | 随机 | 同上 |

**LRU vs LFU**：LRU（最近最少使用）淘汰最久未访问的 key，但可能把偶尔被访问一次的冷数据保留。LFU（最不经常使用）淘汰访问频率最低的，更适合有稳定热点的场景。Redis 的 LRU 是近似实现，通过随机采样（默认采样 5 个）选最久未用的淘汰，而非维护全局链表，牺牲精度换性能。

```redis
# 配置淘汰策略
CONFIG SET maxmemory-policy allkeys-lru
# 配置 LRU 采样数量
CONFIG SET maxmemory-samples 10
```

#### 面试题

**Q：Redis 内存满了怎么办？**

A：Redis 内存达到 maxmemory 限制时，根据淘汰策略处理。8 种策略分三类：noeviction 不淘汰直接拒绝写入；allkeys-* 在所有 key 中淘汰；volatile-* 只在设了过期时间的 key 中淘汰。算法有 LRU（淘汰最久未用）、LFU（淘汰最少使用）、TTL（优先淘汰快过期的）、random（随机）。纯缓存场景推荐 allkeys-lru 或 allkeys-lfu，有持久化数据时用 volatile-lru 只淘汰缓存不淘汰持久化数据。Redis 的 LRU 是近似算法，随机采样 5 个 key 选最久未用的淘汰，不是精确 LRU，可通过 `maxmemory-samples` 调大采样数提升精度。

### 2.5 主从 + 哨兵 + Cluster

#### 主从复制（全量 + 增量）

- **全量同步**：从库首次连接主库时，主库执行 bgsave 生成 RDB 发给从库，同时将 RDB 期间的新写命令缓存在复制缓冲区，RDB 发完后把缓冲区命令发给从库。
- **增量同步**：从库断线重连后，如果断线时间短、offset 差距小，主库从 repl_backlog 环形缓冲区中补发差异命令即可，不需要全量同步。

#### 哨兵 Sentinel（故障转移、选举）

哨兵独立部署，监控主从集群：

1. **监控**：定期 ping 主从节点，判断是否存活。
2. **故障判定**：主观下线（单个哨兵判定不可达）→ 客观下线（超过 quorum 个哨兵同意）。
3. **选举新主**：哨兵选出一个 leader 执行故障转移，从从库中选优先级最高、offset 最大、runid 最小的作为新主库。
4. **通知**：通知客户端和其他从库新主库地址。

#### Cluster（16384 槽位、Gossip 协议）

Redis Cluster 去中心化，无中心代理节点：

- **16384 个槽位**：集群把所有 key 哈希到 16384 个槽中，每个节点负责一部分槽。`slot = CRC16(key) mod 16384`。
- **Gossip 协议**：节点间通过 Gossip 协议互相通信，交换节点状态（存活、槽位分布），每个节点都知道整个集群的拓扑。
- **为什么是 16384**：Redis 作者 antirez 解释，16384 = 2048 字节的位图，节点心跳包中用 2048 字节位图表示自己负责的槽位即可，8192 个节点绰绰有余，同时控制了心跳包大小。

```redis
# 集群中 key 路由
CLUSTER KEYSLOT mykey   # 计算 mykey 所属槽位
# 如果 key 不在当前节点，返回 MOVED 重定向
```

#### 哨兵 vs Cluster 对比

| | 哨兵 Sentinel | Cluster |
|---|-------------|---------|
| 架构 | 主从 + 哨兵监控 | 多主多从，去中心化 |
| 数据分片 | 不分片，全量数据在主库 | 数据分散到多节点 |
| 扩容 | 单主库容量上限 | 可水平扩容加节点加槽 |
| 客户端 | 连哨兵获取主库地址 | 连任意节点，MOVED 重定向 |
| 适用规模 | 中小规模（单主扛得住） | 大规模（数据量超单机内存） |

#### 面试题

**Q：Redis 哨兵和 Cluster 的区别？**

A：哨兵模式是"一主多从 + 哨兵监控"，哨兵负责故障检测和自动故障转移，但不做数据分片，所有数据在一个主库上，受单机内存限制。Cluster 是去中心化的多主多从集群，数据通过 CRC16 哈希分散到 16384 个槽位上，每个主节点负责一部分槽，可以水平扩展容量。哨兵适合中小规模、写量不大、数据能放单机的场景；Cluster 适合数据量超过单机内存、需要水平扩展的场景。两者可以理解为：哨兵解决高可用问题（主库宕机自动切换），Cluster 同时解决高可用和水平扩展问题。Cluster 内置了主从复制和故障转移，不需要额外哨兵进程。

### 2.6 缓存穿透 / 击穿 / 雪崩

| 问题 | 本质 | 典型场景 | 解决方案 |
|------|------|---------|---------|
| 穿透 | 查询不存在的数据，缓存和数据库都没有 | 恶意攻击（查不存在的ID） | 布隆过滤器、空值缓存 |
| 击穿 | 热点 key 过期瞬间大量请求打到数据库 | 秒杀商品缓存过期 | 互斥锁、热点 key 永不过期 |
| 雪崩 | 大量 key 同时过期，请求全部打到数据库 | 批量缓存设置了相同过期时间 | 随机过期时间、多级缓存 |

#### 穿透：布隆过滤器、空值缓存

```java
// 布隆过滤器拦截不存在的 key
// 初始化时把数据库所有 ID 放入布隆过滤器
bloomFilter.put(1L);
bloomFilter.put(2L);

public Object getUser(Long id) {
    // 布隆过滤器判断不存在，直接返回，不查缓存和数据库
    if (!bloomFilter.mightContain(id)) {
        return null;
    }
    Object user = redis.get("user:" + id);
    if (user != null) {
        return user;
    }
    // 缓存未命中，查数据库
    user = db.queryById(id);
    if (user == null) {
        // 空值缓存，设短过期时间防止穿透
        redis.set("user:" + id, "", 60);
        return null;
    }
    redis.set("user:" + id, user, 3600);
    return user;
}
```

#### 击穿：互斥锁

```java
// 热点 key 过期时，用互斥锁只让一个线程去查数据库重建缓存
public Object getHotKey(String key) {
    Object value = redis.get(key);
    if (value != null) {
        return value;
    }
    // 获取互斥锁
    if (redis.setnx("lock:" + key, "1", 10, TimeUnit.SECONDS)) {
        try {
            // 双重检查
            value = redis.get(key);
            if (value != null) {
                return value;
            }
            value = db.query(key);
            redis.set(key, value, 3600);
            return value;
        } finally {
            redis.del("lock:" + key);
        }
    }
    // 等待后重试
    Thread.sleep(50);
    return getHotKey(key);
}
```

#### 雪崩：随机过期时间

```java
// 给缓存过期时间加随机值，避免同时过期
int expire = 3600 + random.nextInt(600);  // 3600~4200秒
redis.set(key, value, expire);
```

#### 面试题

**Q：缓存穿透、击穿、雪崩的区别和解决方案？**

A：三者都是缓存失效导致请求打到数据库，但触发条件不同。穿透是查询缓存和数据库都不存在的数据，每次都穿过缓存打到数据库，常见于恶意攻击，用布隆过滤器前置拦截或缓存空值解决。击穿是单个热点 key 过期的瞬间，大量并发请求同时打到数据库，用互斥锁（只让一个线程查库重建缓存）或逻辑过期（key 不设过期，后台异步更新）解决。雪崩是大量 key 同时过期，用随机过期时间打散过期点、多级缓存（本地 + Redis）兜底解决。核心区别：穿透是"查不存在的"，击穿是"热点 key 过期"，雪崩是"大量 key 同时过期"。

### 2.7 分布式锁

#### SETNX + 过期时间

最简单的分布式锁用 `SETNX`（SET if Not eXists）实现：

```redis
# 加锁（原子操作：SET key value NX EX seconds）
SET lock:order:10086 1 NX EX 30

# 释放锁需要先判断是否是自己的锁，用 Lua 脚本保证原子性
# 如果直接 DEL 可能误删别人的锁
```

**存在的问题**：
1. 业务执行超过锁过期时间，锁自动释放后被别人获取，自己执行完误删了别人的锁。
2. 锁过期但业务未完成，没有续期机制。
3. Redis 单机宕机，锁丢失。

#### Redisson 看门狗机制

Redisson 是 Redis 的 Java 客户端，提供了功能完善的分布式锁实现：

```java
RLock lock = redissonClient.getLock("lock:order:10086");
lock.lock();  // 默认30秒过期，看门狗每10秒续期到30秒
// 或指定超时时间
lock.lock(30, TimeUnit.SECONDS);
try {
    // 执行业务逻辑
} finally {
    lock.unlock();
}
```

**看门狗（Watchdog）机制**：如果调用 `lock()` 不指定过期时间，Redisson 启动一个定时任务（每 10 秒），检查持有锁的线程是否还在执行，如果还在就续期到 30 秒。业务执行完 `unlock()` 后取消定时任务。这样锁不会因为业务执行时间长而过早释放。

Redisson 锁还支持：
- **可重入**：同一线程可多次获取锁，通过 Hash 结构记录重入次数。
- **公平锁**：按请求顺序获取锁。
- **读写锁**：读读共享、读写互斥。

#### RedLock 算法

RedLock 解决单点 Redis 分布式锁的可靠性问题：

1. 获取当前时间。
2. 依次向 N 个（通常 5 个）独立 Redis 实例请求加锁，每个请求设短超时时间。
3. 如果获取了 majority（多数，即 N/2+1 = 3 个）以上的锁，且总耗时小于锁过期时间，则加锁成功。
4. 加锁失败时，向所有实例释放锁。

**争议**：Martin Kleppmann 指出 RedLock 依赖系统时钟，如果某节点发生 GC pause 或时钟跳变，可能导致锁失效。antirez 对此有反驳。生产中如果对正确性要求极高，建议用 ZooKeeper / etcd 的分布式锁。

#### 面试题

**Q：Redis 如何实现分布式锁？**

A：最简单的方式是 `SET key value NX EX seconds`，NX 保证互斥，EX 设过期防死锁。但这种方式有锁过期但业务未完成的问题。生产中通常用 Redisson：调用 `lock()` 不传过期时间会自动启动看门狗，每 10 秒续期到 30 秒，业务执行完 `unlock()` 取消续期，避免锁过期误删。Redisson 还支持可重入锁（Hash 结构记录重入次数）、公平锁、读写锁。对可靠性要求更高时用 RedLock 算法，向多个独立 Redis 实例加锁，获取多数即成功，避免单点故障。但 RedLock 依赖时钟，GC pause 可能导致问题，对正确性要求极高时建议用 ZooKeeper。

### 2.8 事务与 Lua 脚本

#### MULTI/EXEC/DISCARD/WATCH

Redis 事务不是真正的原子事务，而是一组命令的顺序执行：

| 命令 | 作用 |
|------|------|
| MULTI | 开启事务，后续命令进入队列 |
| EXEC | 执行队列中的所有命令 |
| DISCARD | 放弃事务，清空队列 |
| WATCH key | 乐观锁，监控 key，事务执行前若被修改则放弃 |

```redis
# WATCH 实现乐观锁（扣减库存）
WATCH stock:10086
stock = GET stock:10086        # 读取当前库存
MULTI
DECR stock:10086               # 入队
EXEC                           # 执行，执行前检查 stock:10086 是否被改
# 如果在 WATCH 后 EXEC 前，stock:10086 被其他客户端修改了，EXEC 返回 nil，事务放弃
```

**Redis 事务的局限**：
- 命令入队时不会报错（语法错误除外），执行时某条命令失败不影响后续命令继续执行，不支持回滚。
- WATCH 只能检测到 key 被修改，无法像数据库事务那样保证 ACID。

#### Lua 脚本原子性

Redis 用单线程执行命令，执行 Lua 脚本期间不会被其他命令打断，天然原子性。复杂的多步操作用 Lua 脚本比用 WATCH 乐观锁更可靠高效。

```lua
-- Lua 脚本实现原子扣减库存
-- KEYS[1] = 库存key, ARGV[1] = 扣减数量
local stock = redis.call('GET', KEYS[1])
if not stock then
    return -1  -- key不存在
end
if tonumber(stock) < tonumber(ARGV[1]) then
    return 0  -- 库存不足
end
redis.call('DECRBY', KEYS[1], ARGV[1])
return 1  -- 成功
```

```java
// Java 调用 Lua 脚本（Jedis）
String script = 
    "local stock = redis.call('GET', KEYS[1]) " +
    "if not stock then return -1 end " +
    "if tonumber(stock) < tonumber(ARGV[1]) then return 0 end " +
    "redis.call('DECRBY', KEYS[1], ARGV[1]) return 1";

Object result = jedis.eval(
    script, 
    Collections.singletonList("stock:10086"), 
    Collections.singletonList("1")
);
```

#### Redis 事务 vs MySQL 事务

| | Redis 事务 | MySQL 事务 |
|---|-----------|-----------|
| 原子性 | 不支持回滚，命令间独立 | 支持，可 ROLLBACK |
| 隔离性 | 单线程串行执行，天然隔离 | MVCC + 锁机制 |
| 持久性 | 依赖 RDB/AOF，不保证 | redo log 保证 |
| 一致性 | 弱 | 强 |
| 回滚 | 不支持 | 支持 |
| 适用场景 | 乐观锁、批量减少网络开销 | 业务数据一致性保证 |

#### 面试题

**Q：Redis 事务和 MySQL 事务的区别？**

A：核心区别在于 Redis 事务不支持回滚，不是真正的 ACID 事务。Redis 事务用 MULTI 开启后命令入队，EXEC 依次执行，某条命令失败不会中断后续命令也不会回滚已执行的命令。MySQL 事务支持原子性，任一语句失败可 ROLLBACK 回滚全部。隔离性方面 Redis 单线程串行执行天然隔离，MySQL 靠 MVCC 和锁实现。持久性方面 Redis 依赖 RDB/AOF 可能丢数据，MySQL 靠 redo log 保证持久。所以 Redis 事务不能替代 MySQL 事务，它的价值在于减少网络 RTT（批量命令一次发送）和配合 WATCH 实现乐观锁。需要严格原子性的操作（如扣减库存）建议用 Lua 脚本，Redis 单线程执行 Lua 脚本期间不会被其他命令打断，天然保证原子性。
