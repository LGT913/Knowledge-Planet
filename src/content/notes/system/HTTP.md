## 三、HTTP

### 3.1 HTTP 版本演进

| 特性 | HTTP/1.0 | HTTP/1.1 | HTTP/2.0 | HTTP/3.0 |
|------|----------|----------|----------|----------|
| 连接模型 | 短连接（每请求一连接） | 长连接 Keep-Alive | 长连接 + 多路复用 | QUIC 长连接 |
| 请求并发 | 串行 | 管线化（有队头阻塞） | 多路复用（同连接并发） | 多路复用（无 TCP 队头阻塞） |
| 数据格式 | 文本 | 文本 | 二进制分帧 | 基于 QUIC（UDP） |
| 首部压缩 | 无 | 无 | HPACK | QPACK |
| 服务端推送 | 无 | 无 | Server Push | 支持 |
| Host 头 | 无（不支持虚拟主机） | 有 | 有 | 有 |
| 底层协议 | TCP | TCP | TCP（TLS 可选） | QUIC（UDP） |
| 队头阻塞 | 有 | 有（TCP 层 + 管线化） | 有（TCP 层） | 无（流独立） |

**演进动因**：1.0 每请求建连开销大 → 1.1 复用连接；1.1 管线化有队头阻塞 → 2.0 多路复用解决应用层队头阻塞，但 TCP 层仍有；3.0 直接换底层为 QUIC（UDP），彻底消除 TCP 层队头阻塞，并支持连接迁移。

#### 面试题

**Q：HTTP/2 相比 1.1 有什么改进？**

参考答案：HTTP/2 引入二进制分帧，将请求/响应拆为带流 ID 的帧，在一条 TCP 连接上多路复用并发传输，解决了 1.1 应用层的队头阻塞；引入 HPACK 首部压缩减少开销；支持服务端推送。但 HTTP/2 仍跑在 TCP 上，单个流丢包会导致整个 TCP 连接的队头阻塞，HTTP/3 用 QUIC 解决了这一点。

**Q：HTTP/3 为什么用 UDP？**

参考答案：HTTP/2 虽然应用层多路复用，但底层 TCP 一旦丢包，整个连接所有流都被阻塞（TCP 层队头阻塞）。QUIC 在 UDP 上自建可靠传输和流控，每个流独立，一个流丢包不影响其他流。同时 QUIC 将传输层握手与 TLS 握手合并，支持 0-RTT 建连，还支持连接迁移（IP 变化不断连）。

### 3.2 请求方法与幂等性

| 方法 | 语义 | 幂等 | 安全 | 允许 body |
|------|------|------|------|-----------|
| GET | 获取资源 | 是 | 是 | 否（规范） |
| POST | 创建资源 | 否 | 否 | 是 |
| PUT | 整体替换资源 | 是 | 否 | 是 |
| DELETE | 删除资源 | 是 | 否 | 否 |
| PATCH | 局部修改资源 | 否 | 否 | 是 |
| HEAD | 只取响应头 | 是 | 是 | 否 |
| OPTIONS | 查询支持的方法 | 是 | 是 | 否 |

- **幂等**：同一请求执行多次与一次效果相同。
- **安全**：不改变服务端状态。

GET 幂等是因为多次获取同一资源结果一致；PUT 幂等是因为整体替换，重复执行结果仍是最终状态；POST 不幂等是因为每次创建可能生成新资源（如新增订单）；DELETE 幂等是因为删除后再删结果都是不存在。

#### 面试题

**Q：GET 和 POST 的区别？**

参考答案：语义上 GET 用于获取资源、幂等且安全，POST 用于创建/提交、非幂等且不安全。参数位置上 GET 一般放 URL 查询串（受 URL 长度限制、被缓存、暴露在日志），POST 放 body（长度无硬性限制、不缓存）。但需注意 HTTP 规范并没禁止 GET 带 body，也没限制 URL 长度（是浏览器/服务器限制）。安全性上两者都是明文（非 HTTPS），都不适合放敏感信息。本质上 GET/POST 都是 HTTP 请求，技术上能互相替代，差异在语义和约定。

**Q：PUT 和 PATCH 的区别？**

参考答案：PUT 是整体替换，客户端需提供完整资源，重复执行幂等；PATCH 是局部修改，只发送变更字段。重复 PATCH 可能不幂等（如"年龄+1"），但按最终状态补丁则幂等。需要资源完整时用 PUT，只想改部分字段时用 PATCH，减少传输量和并发冲突。

### 3.3 状态码大全

| 类别 | 含义 | 常见状态码 |
|------|------|------------|
| 1xx | 信息性 | 100 Continue |
| 2xx | 成功 | 200 OK、201 Created、204 No Content、206 Partial Content |
| 3xx | 重定向 | 301 永久重定向、302 临时重定向、304 Not Modified |
| 4xx | 客户端错误 | 400 Bad Request、401 Unauthorized、403 Forbidden、404 Not Found、405 Method Not Allowed、429 Too Many Requests |
| 5xx | 服务端错误 | 500 Internal Server Error、502 Bad Gateway、503 Service Unavailable、504 Gateway Timeout |

重点区分：

- **301 vs 302**：301 永久重定向，浏览器会缓存，下次直接跳新地址；302 临时重定向，每次都请求原地址。
- **401 vs 403**：401 未认证（没登录、没带 token），403 已认证但无权限（登录了但没权限访问）。
- **502 vs 504**：502 网关收到上游无效响应（上游崩了），504 网关等上游响应超时（上游太慢）。

#### 面试题

**Q：常见 HTTP 状态码有哪些？**

参考答案：2xx 成功（200 OK、201 Created、204 无内容、206 范围请求）；3xx 重定向（301 永久、302 临时、304 未修改用缓存）；4xx 客户端错误（400 参数错、401 未认证、403 无权限、404 不存在、429 限流）；5xx 服务端错误（500 内部错误、502 网关错误、503 不可用、504 网关超时）。

**Q：301 和 302 的区别？**

参考答案：301 永久重定向，搜索引擎和浏览器会缓存，后续请求直接走新地址，用于域名迁移、HTTP 转 HTTPS；302 临时重定向，不缓存，每次仍请求原地址，用于临时跳转（如登录后跳回）。301 会改变搜索引擎收录，使用要谨慎。

### 3.4 Cookie / Session / Token

| 维度 | Cookie | Session | Token（JWT） |
|------|--------|---------|--------------|
| 存储位置 | 客户端（浏览器） | 服务端（内存/Redis） | 客户端 |
| 状态 | 有状态 | 有状态 | 无状态 |
| 安全性 | 较低（可被窃取） | 较高（仅存 sessionId 到客户端） | 取决于签名与存储 |
| 扩展性 | 差（依赖单机或共享存储） | 差（需共享 Session 存储） | 好（无状态，易水平扩展） |
| 大小限制 | ~4KB | 无（服务端） | 无硬限制 |
| 跨域 | 受同源策略限制 | 依赖 Cookie 传递 sessionId | 可跨域（放 Header） |
| CSRF 风险 | 有（自动带 Cookie） | 有（同上） | 低（不自动携带） |

**Cookie 安全属性**：

- `HttpOnly`：禁止 JS 读取，防 XSS 盗取。
- `Secure`：仅 HTTPS 传输。
- `SameSite=Strict/Lax/None`：限制跨站携带，防 CSRF。

**JWT 结构**：`Header.Payload.Signature`，三段 Base64URL 用 `.` 连接。Payload 携带声明，Signature 用密钥对前两段签名，服务端验证签名即可信任，无需查存储。

#### 面试题

**Q：Cookie、Session、Token 的区别？**

参考答案：Cookie 是客户端存储机制，浏览器自动随请求携带，适合存少量非敏感数据。Session 是服务端会话状态，客户端只存一个 sessionId（通常放 Cookie），服务端根据 sessionId 找到会话数据，安全性高但服务端有状态、难扩展。Token（如 JWT）是无状态凭证，服务端签名后下发，客户端保存并放 Header 携带，服务端验签即信任，无需存储，天然支持分布式。Token 易扩展、防 CSRF（不自动携带），但一旦签发难以主动失效（需黑名单或刷新机制）。

**Q：JWT 怎么实现主动失效？**

参考答案：JWT 无状态，签发后服务端不存记录，正常情况无法主动失效。常见方案：维护一个短期黑名单（放 Redis），登出时把 token 的 jti 加入黑名单，验签时检查是否在黑名单；或采用短有效期 access token + 长 refresh token，access token 过期后用 refresh token 换新，登出时使 refresh token 失效。本质是引入少量状态换取可控性。

### 3.5 HTTPS 握手过程

HTTPS = HTTP + TLS。TLS 握手协商对称密钥，之后用对称加密传业务数据。

#### TLS 1.2 握手（2-RTT）

```
Client                                     Server
  |                                          |
  |  -- ClientHello (TLS版本, 加密套件, 随机数) -> |
  |                                          |
  |  <- ServerHello (选定套件, 随机数) -------- |
  |  <- Certificate (服务端证书) ------------- |
  |  <- ServerKeyExchange (DH 参数) --------- |
  |  <- ServerHelloDone ------------------- |
  |                                          |
  |  -- ClientKeyExchange (DH 公开值) -------> |
  |  -- ChangeCipherSpec / Finished --------> |
  |                                          |
  |  <- ChangeCipherSpec / Finished -------- |
  |                                          |
  |  ========= 对称加密通信 ================== |
```

两个 RTT 后协商出对称密钥（基于两个随机数 + 预主密钥/ DH 参数计算），开始加密通信。

#### TLS 1.3 握手（1-RTT）

TLS 1.3 精简了加密套件、合并了握手消息，ClientHello 直接带密钥交换参数，服务端 Hello 同时完成密钥交换，1-RTT 完成握手。还支持 0-RTT（基于 PSK，客户端可在第一个包就带加密数据，适合重连）。

#### TLS 1.2 vs 1.3 差异

| 维度 | TLS 1.2 | TLS 1.3 |
|------|---------|---------|
| 握手 RTT | 2-RTT | 1-RTT（0-RTT 重连） |
| 加密套件 | 含非前向安全的 RSA 密钥交换 | 仅 ECDHE 等前向安全算法 |
| 签名算法 | 较多（含弱算法） | 精简为安全算法 |
| 公钥/对称加密 | RSA/DH/AES- CBC 等 | 仅 ECDHE + AEAD（GCM/ChaCha20） |
| 前向安全 | 部分套件不支持 | 强制支持 |
| 报文数量 | 较多 | 合并精简 |

**为什么需要证书**：服务端证书由 CA 签名，客户端用预置的 CA 公钥验证证书合法性，防止中间人冒充。证书包含服务端公钥和身份信息，确保握手中的公钥属于真正的服务端。

**前向安全**：使用 ECDHE 时，对称密钥由双方临时密钥对协商，私钥不参与密钥生成；即使服务端长期私钥日后泄露，之前已抓包的流量也无法被解密（临时密钥已销毁）。

#### 面试题

**Q：描述 HTTPS 握手过程。**

参考答案：客户端发 ClientHello，带上支持的 TLS 版本、加密套件和客户端随机数；服务端回 ServerHello 选定套件、给服务端随机数，并发送证书、密钥交换参数。客户端验证证书（CA 签名链、域名、有效期、吊销状态），用证书公钥或 DH 协商出预主密钥，结合两个随机数生成会话密钥；客户端发 ChangeCipherSpec 和 Finished，服务端校验后回同样消息。此后用对称密钥加密通信。TLS 1.3 把密钥交换提前到 ClientHello，握手缩到 1-RTT。

**Q：HTTPS 为什么用混合加密？**

参考答案：非对称加密（RSA/ECDHE）安全但慢，适合握手阶段协商对称密钥；对称加密快，适合后续大流量业务数据。握手用非对称保证密钥协商安全（防中间人），通信用对称保证性能。两者结合兼顾安全与效率。证书用于身份认证，前向安全的 ECDHE 保证即使长期私钥泄露历史流量也安全。

### 3.6 HTTP 长连接与管线化

#### 长连接（Keep-Alive）

HTTP/1.1 默认开启 `Connection: keep-alive`，一条 TCP 连接可发多个请求，避免每次建连的三次握手和慢启动开销。连接空闲一段时间后关闭。

#### 管线化（Pipelining）

HTTP/1.1 允许管线化：客户端可连续发出多个请求不必等响应，服务端按顺序返回。但响应必须按请求顺序（FIFO），前一个响应慢会阻塞后续——即应用层队头阻塞。且管线化要求幂等请求、代理支持差，浏览器默认关闭。

#### HTTP/2 多路复用

HTTP/2 把请求/响应拆为带流 ID 的二进制帧，一条连接上多个流并发交错传输，互不阻塞，真正解决了应用层队头阻塞。

```
HTTP/1.1 管线化：  req1 -> req2 -> req3 ...     resp1 -> resp2 -> resp3 (顺序阻塞)
HTTP/2 多路复用：   流1帧 | 流2帧 | 流1帧 | 流3帧 ...  (交错并发)
```

#### 面试题

**Q：HTTP Keep-Alive 和 TCP Keepalive 一样吗？**

参考答案：不一样。HTTP Keep-Alive 是应用层语义，复用 TCP 连接发多个 HTTP 请求，减少建连开销；TCP Keepalive 是传输层保活机制，检测连接是否存活。两者解决不同问题，名字相似但层次和目的不同。

**Q：管线化和多路复用的区别？**

参考答案：管线化是 HTTP/1.1 的，客户端可连续发请求但响应必须按顺序返回，前一个慢就阻塞后面（队头阻塞）。多路复用是 HTTP/2 的，请求拆成帧按流 ID 并发交错传输，各流独立，一个流慢不影响其他流。管线化因队头阻塞和兼容性问题未被广泛使用，多路复用才是真正的并发。
