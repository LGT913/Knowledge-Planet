### 2.5 主从 + 哨兵 + Cluster

#### 主从复制（全量 + 增量）

- **全量同步**：从库首次连接主库时，主库执行 bgsave 生成 RDB 发给从库，同时将 RDB 期间的新写命令缓存在复制缓冲区，RDB 发完后把缓冲区命令发给从库。
- **增量同步**：从库断线重连后，如果断线时间短、offset 差距小，主库从 repl_backlog 环形缓冲区中补发差异命令即可，不需要全量同步。

#### 哨兵 Sentinel（故障转移、选举）

哨兵独立部署，监控主从集群：

1. **监控**：定期 ping 主从节点，判断是否存活。
2. **故障判定**：主观下线（单个哨兵判定不可达）→ 客观下线（超过 quorum 个哨兵同意）。
3. **选举新主**：哨兵选出一个 leader 执行故障转移，从从库中选优先级最高、offset 最大、runid 最小的作为新主库。
4. **通知**：通知客户端和其他从库新主库地址。

#### Cluster（16384 槽位、Gossip 协议）

Redis Cluster 去中心化，无中心代理节点：

- **16384 个槽位**：集群把所有 key 哈希到 16384 个槽中，每个节点负责一部分槽。`slot = CRC16(key) mod 16384`。
- **Gossip 协议**：节点间通过 Gossip 协议互相通信，交换节点状态（存活、槽位分布），每个节点都知道整个集群的拓扑。
- **为什么是 16384**：Redis 作者 antirez 解释，16384 = 2048 字节的位图，节点心跳包中用 2048 字节位图表示自己负责的槽位即可，8192 个节点绰绰有余，同时控制了心跳包大小。

```redis
# 集群中 key 路由
CLUSTER KEYSLOT mykey   # 计算 mykey 所属槽位
# 如果 key 不在当前节点，返回 MOVED 重定向
```

#### 哨兵 vs Cluster 对比

| | 哨兵 Sentinel | Cluster |
|---|-------------|---------|
| 架构 | 主从 + 哨兵监控 | 多主多从，去中心化 |
| 数据分片 | 不分片，全量数据在主库 | 数据分散到多节点 |
| 扩容 | 单主库容量上限 | 可水平扩容加节点加槽 |
| 客户端 | 连哨兵获取主库地址 | 连任意节点，MOVED 重定向 |
| 适用规模 | 中小规模（单主扛得住） | 大规模（数据量超单机内存） |

#### 面试题

**Q：Redis 哨兵和 Cluster 的区别？**

A：哨兵模式是"一主多从 + 哨兵监控"，哨兵负责故障检测和自动故障转移，但不做数据分片，所有数据在一个主库上，受单机内存限制。Cluster 是去中心化的多主多从集群，数据通过 CRC16 哈希分散到 16384 个槽位上，每个主节点负责一部分槽，可以水平扩展容量。哨兵适合中小规模、写量不大、数据能放单机的场景；Cluster 适合数据量超过单机内存、需要水平扩展的场景。两者可以理解为：哨兵解决高可用问题（主库宕机自动切换），Cluster 同时解决高可用和水平扩展问题。Cluster 内置了主从复制和故障转移，不需要额外哨兵进程。
