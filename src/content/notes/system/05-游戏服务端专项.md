## 一、网络通信

### 1.1 自定义协议设计

游戏通信协议通常采用二进制定长头格式：

| 字段 | 长度 | 说明 |
|------|------|------|
| 魔数 magic | 2 字节 | 校验包合法性，防垃圾数据 |
| 版本号 version | 1 字节 | 协议升级兼容 |
| 消息号 msgId | 2 字节 | 路由分发到对应 Handler |
| 序列号 seq | 4 字节 | 请求-响应配对、重传 |
| 长度 length | 4 字节 | body 字节数，用于拆包 |
| body | 变长 | 序列化后的业务数据 |

```java
// 自定义编码器：将业务对象编码为协议字节
public class GameEncoder extends MessageToByteEncoder<Request> {
    @Override
    protected void encode(ChannelHandlerContext ctx, Request msg, ByteBuf out) {
        out.writeShort(0x1234);          // 魔数
        out.writeByte(1);               // 版本
        out.writeShort(msg.getMsgId());  // 消息号
        out.writeInt(msg.getSeq());      // 序列号
        byte[] body = ProtobufUtil.toBytes(msg.getBody());
        out.writeInt(body.length);       // 长度
        out.writeBytes(body);            // body
    }
}
```

> **面试题：如何设计游戏网络协议？**
> 答：通常采用"二进制定长头 + 变长 body"。定长头包含魔数（校验合法性）、消息号（路由分发）、序列号（请求配对/重传）、长度字段（拆包）。body 用 Protobuf 等高效序列化。魔数能快速丢弃非法包；长度字段配合 Netty LengthFieldBasedFrameDecoder 解决半包。相比 JSON，二进制协议体积小、解析快，适合实时游戏。

### 1.2 Protobuf / Thrift 序列化

| 序列化方式 | 体积 | 速度 | 可读性 | 兼容性 | 适用场景 |
|-----------|------|------|--------|--------|---------|
| **Protobuf** | 极小 | 极快 | 差（二进制） | 前向兼容好 | 游戏内通信、高频消息 |
| Thrift | 小 | 快 | 差 | 一般 | 跨语言 RPC |
| JSON | 大 | 慢 | 好 | 灵活 | 后台接口、调试 |

```protobuf
// player.proto
syntax = "proto3";
message PlayerInfo {
    int64 playerId = 1;
    string name = 2;
    int32 level = 3;
    float x = 4;
    float y = 5;
}
```

> **面试题：游戏服务端为什么选 Protobuf 而不是 JSON？**
> 答：Protobuf 体积小（紧凑二进制）、解析速度快、字段编号设计支持前向兼容（新增字段不影响旧版本）。游戏消息高频、对带宽和延迟敏感，Protobuf 能显著降低带宽占用和 CPU 开销。缺点是可读性差，调试需配合工具；JSON 易读但体积大、解析慢，适合后台管理接口而非实时战斗。

### 1.3 粘包拆包处理

TCP 是流式协议，无消息边界，多条消息可能合并或被拆开。Netty 提供多种解码器：

- **LengthFieldBasedFrameDecoder**：基于长度字段（游戏最常用）。
- FixedLengthFrameDecoder：固定长度。
- DelimiterBasedFrameDecoder：分隔符。

```java
// 协议头中 length 字段在 [0,4) 位置，长度4字节
// lengthAdjustment=0 表示 length 就是 body 长度
// initialBytesToStrip=4 表示解码后去掉长度字段本身
p.addLast(new LengthFieldBasedFrameDecoder(
    65535,   // maxFrameLength
    0,       // lengthFieldOffset 长度字段偏移（前面是魔数/版本/消息号时需调整）
    4,       // lengthFieldLength 长度字段长度
    0,       // lengthAdjustment 长度调整
    4));     // initialBytesToStrip 跳过字节数
```

> **面试题：Netty 如何处理粘包？**
> 答：应用层自定义消息边界。游戏协议用长度字段法最通用——在包头放一个 length 字段表示 body 长度，配合 LengthFieldBasedFrameDecoder，它会读长度字段并截取一帧完整数据，不足则等待。这样无论 TCP 如何粘包拆包，都能正确还原一条条消息。

### 1.4 连接管理

- 维护 `channelMap<playerId, Channel>` 建立玩家与连接的双向映射。
- 登录成功后绑定 playerId 到 Channel（attr）并加入 map。
- 心跳检测：超时未收到心跳则关闭连接并从 map 移除。
- 重连处理：玩家重连后复用旧 channel 数据或重新加载状态。

```java
public class ChannelManager {
    private final Map<Long, Channel> channelMap = new ConcurrentHashMap<>();

    public void bind(Long playerId, Channel channel) {
        Channel old = channelMap.put(playerId, channel);
        if (old != null && old != channel) {
            old.close(); // 顶号下线
        }
        channel.attr(ATTR_PLAYER_ID).set(playerId);
        channel.closeFuture().addListener(f -> channelMap.remove(playerId));
    }

    public Channel getChannel(Long playerId) {
        return channelMap.get(playerId);
    }
}
```

> **面试题：如何管理大量玩家连接？**
> 答：维护 playerId→Channel 的映射表（channelMap），登录成功时绑定并监听 close 事件自动清理。需要处理顶号（同账号重复登录踢掉旧连接）、断线重连（复用状态）、心跳超时清理。高并发下用 ConcurrentHashMap，并可按 playerId 分片降低锁竞争。Channel 自带 attr 可存玩家上下文，避免每次查 map。

## 二、房间与场景

### 2.1 房间状态机

房间典型状态流转：**等待中（WAITING）→ 游戏中（PLAYING）→ 结算中（SETTLING）→ 销毁（DESTROYED）**。状态机保证流转合法性，非法流转拒绝并记录。

```java
public enum RoomState {
    WAITING, PLAYING, SETTLING, DESTROYED
}

public boolean transition(RoomState target) {
    switch (state) {
        case WAITING -> { if (target == PLAYING) { state = target; return true; } }
        case PLAYING -> { if (target == SETTLING) { state = target; return true; } }
        case SETTLING -> { if (target == DESTROYED) { state = target; return true; } }
    }
    throw new IllegalStateException("illegal transition " + state + "->" + target);
}
```

> **面试题：房间状态机如何设计？**
> 答：定义有限状态集（等待→游戏中→结算→销毁），每个状态只允许流转到合法后继状态。流转方法集中校验合法性，非法流转拒绝并告警。状态机避免了并发下"已结算还接收移动"等错误操作。注意流转操作要线程安全（单房间单线程串行处理，或加锁），结算态要持久化结果，销毁态清理资源释放房间池。

### 2.2 AOI 算法

AOI（Area Of Interest，兴趣范围）解决"只广播玩家周围实体"的问题，降低带宽与计算。

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **九宫格** | 地图划分为 3×3 格子，只关心中心格及周围8格 | 实现简单、查询 O(1) | 网格密度需调优、边界跳变 |
| **十字链表** | 每个实体维护 X/Y 双向链表，按坐标排序 | 动态对象少时高效 | 大量对象时维护代价高 |
| **网格法** | 地图均匀分格，格内维护对象列表 | 通用、粒度可调 | 空格子浪费、密度不均 |

```java
// 九宫格 AOI：玩家移动时只更新所在格及周围8格的可见集
public Set<Long> getViewEntities(int gridX, int gridY) {
    Set<Long> view = new HashSet<>();
    for (int dx = -1; dx <= 1; dx++) {
        for (int dy = -1; dy <= 1; dy++) {
            GridCell cell = grids[gridX + dx][gridY + dy];
            if (cell != null) view.addAll(cell.getEntities());
        }
    }
    return view;
}
```

> **面试题：AOI 算法有哪些？各有什么优缺点？**
> 答：常见三种——①九宫格：把地图划成格子，玩家只关心所在格及周围8格，实现简单查询快，但网格密度需调优且边界有跳变；②十字链表：实体按 X/Y 坐标维护双向有序链表，动态对象少时高效，但对象多时链表维护代价高；③网格法：通用粒度可调，适合不规则地图，空格子有浪费。游戏选型取决于地图大小和实体密度，MMO 多用九宫格变种。

### 2.3 状态同步 vs 帧同步

| 维度 | 状态同步 | 帧同步 |
|------|---------|--------|
| 服务端职责 | 计算最终状态并下发 | 只转发玩家操作 |
| 下发内容 | 实体状态（坐标/血量） | 操作输入 + 帧序号 |
| 带宽 | 较大（状态数据多） | 较小（只传操作） |
| 逻辑要求 | 服务端权威、可不一致 | **确定性逻辑**（同输入必同结果） |
| 反外挂 | 强（服务端权威） | 弱（客户端可作弊逻辑） |
| 回放/观战 | 需录制状态 | 重放操作即可 |
| 典型场景 | MMO、FPS | RTS、MOBA（如 DOTA/王者荣耀） |

> **面试题：状态同步和帧同步的区别？**
> 答：状态同步由服务端算出结果（坐标/血量）下发给客户端，服务端权威、防外挂强、回放需录状态，但带宽大；帧同步服务端只转发玩家操作，客户端各自演算，带宽小、回放只需重放操作，但要求逻辑完全确定（不能用浮点、随机需固定种子、遍历顺序需固定），且反外挂弱。MOBA 多用帧同步，MMO/FPS 多用状态同步。

### 2.4 服务端权威

- **移动校验**：客户端发送目标坐标，服务端校验移动速度是否合理（不能瞬移），非法则拒绝/拉回。
- **技能校验**：冷却时间、施法距离、资源消耗、命中判定都在服务端，客户端只做表现。
- **防外挂**：客户端永远不可信，关键判定（伤害结算、拾取、交易）都在服务端。

```java
// 移动校验：根据上次坐标和时间差校验速度
public boolean validateMove(Player p, float newX, float newY, long nowMs) {
    float dx = newX - p.x, dy = newY - p.y;
    double dist = Math.sqrt(dx * dx + dy * dy);
    double elapsedSec = (nowMs - p.lastMoveMs) / 1000.0;
    double maxDist = p.moveSpeed * elapsedSec * TOLERANCE; // 容差因子
    if (dist > maxDist) {
        // 速度异常，拒绝并下发拉回包
        return false;
    }
    p.x = newX; p.y = newY; p.lastMoveMs = nowMs;
    return true;
}
```

> **面试题：服务端权威如何防外挂？**
> 答：核心原则是"客户端不可信"。移动用速度×时间差校验合理性，超速直接拉回；技能冷却、距离、命中全在服务端判定；伤害结算、掉落、交易等关键流程绝不下放客户端。客户端只负责表现层（动画、特效）。配合日志审计和异常行为检测（如单位时间操作频率）识别可疑账号。

## 三、并发与状态

### 3.1 有状态服务

- 游戏服务端多为**有状态**：玩家数据常驻内存（登录时加载、定时落库）。
- 优势：低延迟，避免每帧查 DB。
- 风险：内存与 DB 一致性、宕机数据丢失、扩容时状态迁移。
- 典型方案：玩家上线加载到本地缓存 → 内存操作 → 定时批量落库 → 下线时即时落库。

> **面试题：游戏服务端为什么是有状态服务？有何风险？**
> 答：游戏交互高频、对延迟敏感，玩家数据常驻内存避免每帧查库。风险是数据一致性（内存与 DB 可能不一致）、宕机丢数据、扩容需迁移玩家状态。缓解：定时落库 + 关键操作即时落库 + 内存快照 + 玩家路由固定到某节点（一致性哈希）。也可用"有状态分片 + 无状态网关"混合架构。

### 3.2 无锁化设计

- **Disruptor**：基于环形数组（RingBuffer）的无锁队列，单生产者-多消费者，通过 CAS + 序号屏障实现极高吞吐，常用于日志异步、事件总线。
- **Actor 模型**：每个 Actor 持有私有状态，通过消息（邮箱 mailbox）通信，天然避免共享可变状态，如 Akka。
- **CAS + volatile**：轻量并发原语，无锁但有 ABA/竞争开销问题。

```java
// Disruptor 生产-消费示例
RingBuffer<OrderEvent> ringBuffer = disruptor.getRingBuffer();
long seq = ringBuffer.next();  // 申请序列号（无锁）
try {
    OrderEvent evt = ringBuffer.get(seq);
    evt.setData(order);
} finally {
    ringBuffer.publish(seq);   // 发布，消费者可见
}
```

> **面试题：Disruptor 为什么快？**
> 答：①环形数组替代链表，内存连续、CPU 缓存友好、无 GC 压力；②用单生产者/多消费者模型 + Sequence 序号屏障，减少竞争，多数场景无锁（仅必要的 CAS）；③消除伪共享（填充缓存行）；④消费者依赖关系用序号屏障表达，避免锁。综合下来单机可承载千万级 TPS，适合日志、事件总线、玩家消息分发。

### 3.3 排行榜

- **Redis ZSet**（有序集合）天然适合排行榜：ZADD 加分、ZREVRANGE 取 Top N、ZREVRANK 查个人排名。
- 成员唯一、分数可重复，按分数排序，查询 O(logN)。

```java
// 实时战力排行榜
public void addScore(long playerId, int score) {
    redis.opsForZSet().add("rank:power", String.valueOf(playerId), score);
}
public List<Long> topN(int n) {
    Set<String> ids = redis.opsForZSet().reverseRange("rank:power", 0, n - 1);
    return ids.stream().map(Long::parseLong).toList();
}
public long rank(long playerId) {
    Long r = redis.opsForZSet().reverseRank("rank:power", String.valueOf(playerId));
    return r == null ? -1 : r + 1; // 0-based 转 1-based
}
```

> **面试题：如何用 Redis 实现排行榜？**
> 答：用 ZSet（有序集合）——成员是玩家ID，分数是战力/积分。ZADD 更新分数、ZREVRANGE 取 Top N、ZREVRANK 取个人名次，操作都是 O(logN)。对于全服亿级排行榜可分桶（按分数段分多个 ZSet）或用 Redis Cluster 分片。注意 ZSet 分数相同时按字典序排，如需按时间排可用"分数+时间戳"复合分。

### 3.4 匹配队列

- **ELO 积分**：根据胜负调整积分，相近积分的玩家匹配。
- **等待超时降级**：等待越久放宽匹配条件（积分差范围随时间扩大），避免长等待。
- 数据结构：分桶（按积分区间）+ 优先队列，或 Redis ZSet 按等待时间排序。

```java
// 匹配：先尝试同分段，超时逐步放宽
public List<Player> match(int elo, long waitMs) {
    int range = 100 + (int)(waitMs / 1000) * 50; // 每秒放宽50分
    return pool.stream()
        .filter(p -> Math.abs(p.elo - elo) <= range)
        .sorted(Comparator.comparingLong(p -> p.waitMs))
        .limit(5)
        .toList();
}
```

> **面试题：游戏匹配系统如何设计？**
> 答：核心是"积分相近优先 + 等待越久越宽松"。用 ELO 评估玩家水平，匹配时先在相近分段池中找，匹配成功即组队；等待超时则逐步放宽积分差（每秒扩大若干分）避免长等待。数据结构可按积分分桶（同桶内优先匹配）+ Redis ZSet 按等待时间排序。还需考虑组队匹配（队伍平均分）、跨分段惩罚、高峰期扩容匹配线程等。

## 四、性能优化

### 4.1 对象池

- 高频创建/销毁的对象（子弹、伤害包、玩家消息）用对象池复用，减少 GC 压力与分配开销。
- Netty 的 ByteBuf、Disruptor 的事件对象都基于池化思想。

```java
// 子弹对象池（复用 Bullet 实例）
public class BulletPool {
    private final ConcurrentLinkedQueue<Bullet> pool = new ConcurrentLinkedQueue<>();

    public Bullet acquire() {
        Bullet b = pool.poll();
        return b != null ? b.reset() : new Bullet();
    }
    public void release(Bullet b) {
        if (pool.size() < MAX_SIZE) pool.offer(b);
    }
}
```

> **面试题：游戏中为什么要用对象池？**
> 答：子弹、伤害包、网络包这类对象高频创建销毁，直接 new 会产生大量短命对象，触发频繁 Minor GC 甚至 Full GC，造成延迟抖动（卡顿）。对象池复用已分配实例，acquire 借出、release 归还，把"分配-回收"变为"借用-归还"，显著降低 GC 压力。注意池要限制上限避免内存泄漏，且只用于真正高频对象，否则徒增复杂度。

### 4.2 定时器

- **时间轮（HashedWheelTimer）**：O(1) 添加/取消，适合海量短周期任务（buff/CD 倒计时）。Netty 自带实现。
- **DelayQueue**：基于堆，O(logN)，适合任务数不多的场景。
- **ScheduledThreadPoolExecutor**：基于 DelayQueue 封装。

```java
// 时间轮：给玩家加一个5秒后过期的buff
HashedWheelTimer timer = new HashedWheelTimer();
timer.newTimeout(timeout -> {
    player.removeBuff(BuffType.STUN);
}, 5, TimeUnit.SECONDS);
```

> **面试题：游戏定时器为什么用时间轮？**
> 答：游戏中有海量定时任务（技能 CD、buff 倒计时、复活计时），用 ScheduledThreadPool 的 DelayQueue（堆结构）每次添加/取消是 O(logN)，量大时开销高。时间轮把任务按"到期时间"分到环形槽位，添加和取消都是 O(1)，且单线程推进指针，无锁竞争，特别适合海量短周期定时任务。缺点是精度受 tick 间隔限制，长周期任务需要多轮触发。

### 4.3 日志异步化

- **Log4j2 AsyncLogger**：基于 Disruptor 无锁队列，日志写入异步化，不阻塞业务线程。
- 生产配置：业务线程只入队，独立 IO 线程刷盘。

```xml
<!-- Log4j2 异步日志配置 -->
<Configuration>
  <Appenders>
    <RollingFile name="File" fileName="logs/game.log"
                 filePattern="logs/game-%d{yyyy-MM-dd}-%i.log.gz">
      <PatternLayout pattern="%d %-5p %c{1} %m%n"/>
      <Policies>
        <TimeBasedTriggeringPolicy/>
        <SizeBasedTriggeringPolicy size="200MB"/>
      </Policies>
    </RollingFile>
  </Appenders>
  <!-- AsyncRoot 启用全异步 -->
  <Loggers>
    <AsyncRoot level="info">
      <AppenderRef ref="File"/>
    </AsyncRoot>
  </Loggers>
</Configuration>
```

> **面试题：游戏服务端如何优化日志性能？**
> 答：①用 Log4j2 的 AsyncLogger（基于 Disruptor 无锁队列），业务线程只入队、独立线程刷盘，不阻塞主循环；②合理设置日志级别，线上核心路径只留必要日志，Debug 级关闭；③按需采样（如战斗日志采样1/100）；④IO 用文件而非数据库，并按大小/时间滚动压缩。注意异步日志在 JVM 崩溃时可能丢最后几条，关键错误可同步落盘兜底。

### 4.4 压测工具

| 工具 | 类型 | 适用 |
|------|------|------|
| **JMeter** | 协议压测 | TCP/HTTP 自定义协议、可写脚本 |
| **wrk** | HTTP 压测 | 轻量、高并发、延迟测试 |
| **自建机器人** | 业务压测 | 模拟真实玩家行为链（登录→匹配→战斗） |

> **面试题：游戏服务端如何压测？**
> 答：分两层——网关层用 wrk/JMeter 压 HTTP 接口看吞吐和延迟；业务层自建机器人客户端模拟真实玩家行为链（登录→匹配→战斗→结算），逐步加并发找出瓶颈。重点关注 TPS、P99 延迟、CPU/内存/GC、网络带宽。游戏压测难点在于机器人要还原真实协议交互和状态流转，纯接口压测无法暴露房间逻辑、AOI 广播等热点。压测中观察 GC 频率、EventLoop 队列堆积定位问题。
