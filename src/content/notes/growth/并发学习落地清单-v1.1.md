# Java 并发学习落地清单 v1.1（适配博客真实代码）

> 文档存放位置：项目根目录 `并发学习落地清单 v1.1.md`
> 说明：v1.1 针对 v1.0 的 **P0 立论失真** 与 **P1 线程池复用矛盾** 两处硬伤做了修正，其余保留 v1.0 结论。

## 背景说明
1. 现状：项目**分布式并发能力完备**（Redisson 分布式锁、Redis 计数、MQ 异步、缓存三防）；**JVM 本机并发实战空白**，无 JUC 业务代码；已有 2 个自定义业务隔离线程池 `cacheRebuildExecutor`、`warmupExecutor`。
2. 原则：**不重复造轮子、不破坏现有生产链路、区分【主项目业务改造】和【独立 Demo 验证】**；Demo 单独新建子模块 `concurrent-demo`，不污染博客主业务代码。
3. 学习目标：补齐 JMM、JUC、线程池、异步编排、并发排查能力；面试可以清晰区分**JVM 本机并发**与**分布式并发**，消除"只会堆砌中间件"的质疑。
4. 周期：业余每日 1‑2h，总周期 **4‑5 周**。

## 二、🛠 v1.1 关键修正（相对 v1.0 的两处硬伤）

### 修正 1：P0 立论失真 → 改为「审计 + 最小化并行 + 量化证据」

**代码事实**（`ArticleServiceImpl.getArticleRankingByViews()`）：

| v1.0 计划的分类 | 真实代码 | 能否并行 |
|---|---|---|
| Redis ZSet 查 TOP10 | 1 次调用 | 无 |
| "补查 DB" | `findAllById(missIds)` **已是单次批量查询** | ❌ 无收益 |
| "读取文章详情缓存" | for 循环逐个 `getWithLogicalExpire`（**10 次独立 Redis RTT**） | ✅ **唯一真能并行的** |
| "填充作者信息" | `fillAuthorNames`→`findAllById` **已是单次批量查询** | ❌ 无收益 |

**结论**：该接口大部分环节**早已批量化**，唯一可并行的是那 10 次 Redis 详情读，收益为毫秒级（Redis ~1ms RTT）。照 v1.0 原样"整接口并行 + 复用 cacheRebuildExecutor"属于**过度设计**，甚至会用缓存重建线程池抢 Redis 读、饿死真正要紧的重建线程。

**v1.1 改法（P0，见阶段 3）**：
1. 先给接口各环节加日志，**量化耗时分布**（先取证，再决定改不改）。
2. **只对该 Redis 详情读循环做最小化并行**（用 `CompletableFuture.runAsync(cacheRebuildExecutor)` 或 `allUp()/CompletableFuture.allOf` 并限制并发，避免 10 个任务全量打满）。
3. 记录改造前后耗时，产出对比数据。
4. **收益小则明确写"不值得改，保持串行"** —— 这本身就是面试亮点（体现"知道什么时候不该并行"）。

> 若想找真正扇出更大的 CompletableFuture 落地场景，可考虑"文章详情页拼：详情 + 作者 + 上一篇/下一篇 + 相关推荐"这类多来源聚合接口。

### 修正 2：P1 矛盾 → 导出任务不复用 cacheRebuildExecutor

**矛盾点**：v1.0 既强调"线程池隔离（舱壁模式）"，又要求导出"复用 cacheRebuildExecutor 禁止新建线程池"。但批量导出是**长任务**，与"低延迟缓存重建"的 `cacheRebuildExecutor`（核心 5 / 队列 200 / CallerRuns）**用途冲突**——导出跑得久会占用缓存重建线程。

**v1.1 改法（二选一）**：
- **方案 A（推荐）**：为导出新建一个**独立有界线程池**（如核心 4 / 最大 8 / 队列合理 / 自定义拒绝策略），这才正确体现"隔离"。与"不重复造轮子"不冲突——任务是不同类型，隔离恰恰要求独立池。
- **方案 B（更轻）**：若导出量不大，**不用线程池，改用 `Semaphore` 限制 DB 并发** + 分批 `findAllById` 顺序读取，更简单且不碰公共资源。

> 一句话：**"复用"≠把什么都塞进同一个池；线程池隔离原则允许为不同类型任务开独立池。** 这一条要写进 `线程池设计说明.md`，否则面试官一追问就露。

### 阶段 1：JMM 内存模型 & 线程基础｜5‑7 天
> 核心目标：搞懂多线程 bug 根源：原子性、可见性、有序性；分清并发/并行；线程状态流转。

#### 📖 理论学习
1. 进程与线程；Java 线程为操作系统 1:1 内核线程；并发 vs 并行
2. 线程六大状态：NEW/RUNNABLE/BLOCKED/WAITING/TIMED_WAITING/TERMINATED，状态流转
3. API 辨析：`start()` vs `run()`；`sleep()`/`wait()`/`yield()`/`join()` 区别
4. JMM Java 内存模型：主内存、线程工作内存；三大特性
5. `volatile`：内存屏障，可见性、禁止指令重排序；**不能保证原子性，不能做 count++**；适用场景（开关标志位）
6. `synchronized`：对象头 MarkWord；锁升级：偏向锁→轻量级锁→重量级锁；Monitor；可重入、不可中断

### 阶段 2：JUC 核心（AQS、CAS、锁、工具类）｜10‑12 天
> 核心目标：理解 JUC 底层思想；掌握 CAS、AQS 骨架；掌握 Lock、原子类、三大工具类；分清 **JVM 本地锁 vs Redisson 分布式锁**。

#### 📖 理论学习
1. CAS 原理：Compare And Swap，Unsafe；三大问题：**ABA、自旋空转 CPU 高、不能保护多个变量**；`AtomicStampedReference` 解决 ABA；`LongAdder` 分段累加，对比 AtomicInteger。
2. AQS：`state` 状态变量、CLH 双向阻塞队列；**独占模式、共享模式**；acquire/release 模板方法。（掌握骨架即可，不逐行啃源码）
3. `ReentrantLock`：可重入；公平/非公平；`lock()`/`tryLock()`/`lockInterruptibly()`；unlock 必须在 finally；`Condition` 对比 `wait/notify`。
4. `ReentrantReadWriteLock`：读共享写独占；读多写少；写饥饿问题。
5. 三大工具类：CountDownLatch（不可重置）／CyclicBarrier（可复用）／Semaphore（限流）。
6. ThreadLocal：线程本地副本；**线程池复用的脏数据、内存泄漏坑；必须 try‑finally remove()**；了解 TransmittableThreadLocal。

### 阶段 3：线程池 + 并发容器 + CompletableFuture｜10‑12 天
> 重点：**不重复新建线程池，复盘已有两个线程池；主项目 P0（修正版）；P1 新增后台文章导出（复用修正）**。

#### 📖 理论学习
1. `ThreadPoolExecutor` 七大核心参数；为何不直接用 `Executors` 快捷方法；4 种拒绝策略；线程池 5 种状态；CPU/IO 密集参数估算；**业务线程池隔离（舱壁模式）**。
2. 阻塞队列 `BlockingQueue`：Array/Linked/Synchronous/Priority；生产者‑消费者模型。
3. `ConcurrentHashMap`：1.7 分段锁 vs 1.8 CAS+synchronized 锁桶头；**单方法原子安全，if‑contains‑then‑put 复合操作线程不安全**。
4. `CopyOnWriteArrayList`：写时复制；**读多写极少；高频写性能灾难**。
5. `CompletableFuture`：串行/并行组合；`thenApply`、`thenCombine`、`allOf`；`exceptionally` 异常处理；**重点：异常不主动捕获会被封装、易吞异常**。
6. ForkJoinPool（了解即可）。

## 六、风险与避坑清单
1. ❌ 不要为了用技术而强行改造主业务；LongAdder、ReentrantReadWriteLock 本地缓存**仅 Demo**，不接入真实流量，避免多实例数据不一致。
2. ❌ 不要重复新建线程池；已有两个业务池优先**评审参数**而非重造；但**长任务（如导出）应按隔离原则单开独立池或用 Semaphore 限流**，不要强行塞进 cacheRebuildExecutor。
3. ❌ 不要死磕 AQS 每一行源码；掌握整体架构、state、CLH 队列、独占/共享模式即可。
