## 第 1 题：你这个健康管理具体怎么做的 ✅

**【话术】**
> 我的健康检查是"入口 → 中间件 → 应用"三层做的。
> ① 入口层：Nginx 里挂了 `/health` 探活接口，返回 `200 OK`（[nginx.conf](file:///c:/Users/lenovo/Desktop/blog/blog-cloud/nginx.conf#L65-L69)），负载均衡和运维探活都打这个接口；
> ② 中间件层：MySQL/Redis/RabbitMQ 用 Docker Compose 编排，容器健康状态由 Docker 守护（`docker compose ps` 就能看），RabbitMQ 还配了死信队列，消费失败不会静默丢；
> ③ 应用层：Spring Boot 进程用 systemd 托管，`systemctl status blog.service` 能看存活，`@Scheduled` 定时任务（缓存预热/阅读量批量落库）每次跑完打日志，日志里监控异常。
> 整体思路是：**不只看"进程在不在"，还要看"关键链路能不能通"**，所以探活点放在最外层 Nginx。

**【思路与思考】**
面试官问"健康管理"其实是考你对**探活体系**的理解。核心要传达三点：① 分层（LB/中间件/应用）② 探活接口返回什么（`200`）③ 挂了之后谁来兜底（systemd 重启 / Docker 重启策略）。别只答一句"我配了 /health"。

**【👨‍💻追问】**
- **"TCP 健康检查能检查出什么，和 HTTP 检查区别？"** → 见第 2、3 题话术。
- **"进程活着但假死（线程阻塞）怎么办？"** → TCP/端口探活查不出假死，所以要 HTTP 应用层探活：请求一个真实走 Spring 容器的接口，超时就判 down；还可以配合线程池监控（活跃线程数、队列积压）。

## 第 2 题：TCP 能检查什么，哪些信息 ⚠️

**【话术】**
> 我理解 TCP 健康检查是负载均衡在**传输层**做探活：对后端节点发起一次 TCP 连接（三次握手），看能不能建立连接。能建立的检查信息包括：① **端口是否存活/监听**（connect 是否成功）；② **握手耗时/响应时延**（反映网络和节点负载）；③ **连接能否保持**（部分实现会做一次收发）。它是"粗粒度探活"，只证明"TCP 层活着"，证明不了应用层逻辑是否正常。
> 回到我的项目：blog 单机部署主要用 Nginx `/health` 做 HTTP 层探活，因为单体场景要探的就是"应用能不能处理请求"，TCP 端口探活适合多副本负载均衡场景，我理解原理、没实际配多副本。

**【思路与思考】**
这道题大概率是从"负载均衡的健康检查"延伸的。答题关键：把 TCP 检查的本质（传输层 connect + 时延）讲清楚，再主动点出**局限**（查不出应用假死），顺势引导到你熟悉的 HTTP `/health`——这一手既显深度又拉回主场。

**【👨‍💻追问】**
- **"TCP 探活多久探一次？频率怎么定？"** → 太快会打爆后端（每个节点都被反复探测），太慢故障发现不及时；一般 5~10s 一次，加失败阈值（连续 N 次失败才摘除，防抖动误判）。
- **"探活失败马上摘掉吗？"** → 不会，要有失败计数 + 滑动窗口，避免网络抖动导致节点被误摘、频繁上下线（抖动导致 flapping）。

## 第 3 题：具体可以检测到哪些信息 ⚠️

**【话术】**
> 具体能拿到的信息分两类：
> - **连接性信息**：目标 IP:端口是否可达、是否能完成三次握手、握手 RTT、连接是否被 RST 拒绝（端口没监听会直接拒绝）。
> - **衍生信息**：连续失败次数、当前可用节点数、节点权重、失败后是否触发摘除。
> 如果是 HTTP 探活还能拿到：状态码（200/502/503）、响应体、响应耗时、超时情况。
> 我的 blog 探活用的是 HTTP 方式：Nginx `/health` 固定返回 `200 OK`，我理解"返回 200 + 耗时正常"才是健康，503/超时说明应用层有问题。

**【思路与思考】**
这题是第 2 题的细化，面试官在**追细节**。别重复第 2 题，要往下钻一层：连接性 + 派生统计 + HTTP 层额外信息。最后落到自己的 `/health`，证明你真理解而不是背概念。

## 第 4 题：你在这个项目里面具体做了哪些开发 ✅

**【话术】**
> 这是个从 0 到 1 的全栈博客系统，我按"读链路、写链路、基础设施"三条线开发：
> - **读链路（高频读优化）**：文章详情做了缓存三防——布隆过滤器拦截不存在的 ID 防穿透、Redisson 分布式锁 + DCL 防击穿、TTL 随机抖动防雪崩；列表分页用缓存 + 总数缓存，命中不查库。
> - **写链路（高频写削峰）**：阅读量用 Redis `INCR` 原子自增 + 脏标记，定时批量落库；点赞、浏览记录、AI 摘要生成全部走 RabbitMQ 异步解耦；AI 摘要用 DeepSeek 生成，消费端做幂等（`setIfAbsent`）+ 令牌桶限流 + 死信重试三层保护。
> - **基础设施**：JWT 鉴权 + Redis 禁用标记实现服务端封号；Nginx 反代 + 限流；Docker Compose 部署中间件，单体 → 微服务（Gateway + Nacos + Feign + Sentinel）演进版也做了。

**【思路与思考】**
这道题就是"自我介绍项目版"。别按包名平铺，要**按业务链路讲**，体现"为什么这么做"。重点是突出难点（高频读/高频写）和你对取舍的理解（为什么用 MQ 不用线程池等），这些在第 4 题之后大概率被逐个展开追问。

**【👨‍💻追问】**
- 高频读：缓存三防细节（已有话术，见[面试拷打-博客项目.md](file:///c:/Users/lenovo/Desktop/My-notes/my-notes/面试拷打-博客项目.md)）
- 高频写：MQ 怎么保证不丢、怎么防重复消费
- 微服务：为什么拆、跨服务事务怎么办

## 第 5 题：后端有两个负载，停掉一个只用另一个，这个过程是怎样的 ⚠️

**【话术】**
> 我理解这个场景是"多副本负载均衡下的平滑摘流"。正确流程是：
> ① **摘除**：先在负载均衡（Nginx upstream）里把要停的节点 `down` 掉，或者把权重调成 0——这一步是为了让新请求**不再打过来**；
> ② **排空（drain）**：等存量请求处理完（短连接很快，长连接/WebSocket 要等它自然断开或主动踢）；
> ③ **停服**：再停进程/容器，这样业务无感知；
> ④ **恢复**：节点恢复后重新 `up`，健康检查确认通过，流量逐步切回（可以先用小权重灰度）。
> 回到我的项目：blog 单体是单节点，没有多副本，但我部署用的是 Nginx 反代 + systemd，如果要做多副本，就是在 upstream 里加多个 `server`，通过 `down`/`weight` 控制摘流和放量，原理是同一套。

**【思路与思考】**
这题考**优雅上下线（滚动发布）**思路，核心是"先摘流量、再停服务、恢复时先探活后放量"，顺序错就会产生请求打到已停节点 → 502。重点讲"为什么先摘流量"：因为直接 kill 进程，正在处理的请求会断、新请求会 502。

**【👨‍💻追问】**
- **"WebSocket 长连接怎么办？"** → 长连接摘不掉，要让服务端主动发关闭帧，或等心跳超时回收；Nginx 的 `drain` 对长连接效果有限。
- **"怎么确认存量请求处理完了？"** → 看活跃连接数归零、请求队列空、日志里无 in-flight；短连接场景基本等一个超时窗口即可。

## 第 6 题：在这个过程里面，OpenResty 做了什么事情 ⚠️

**【话术】**
> 先纠正一下：我的 blog 用的是 **Nginx**，不是 OpenResty。OpenResty 是 Nginx + Lua 的高性能扩展版。我理解它在"停一个负载"的过程里做三件事：
> ① **负载均衡**：作为反向代理，按 upstream 配置把请求分发给后端节点；
> ② **健康检查/摘除**：通过主动探活发现节点不可用，把它从可分发集合里剔除，新请求不再转发给它（相当于"停一个负载"的第一步）；
> ③ **流量控制**：`weight` 权重调整、`limit_req` 限流，配合实现平滑摘流。
> 我自己的 [nginx.conf](file:///c:/Users/lenovo/Desktop/blog/blog-cloud/nginx.conf) 里同样做了反代（`proxy_pass` 到 gateway）、限流（`limit_req` 10r/s + `limit_conn`）、`/health` 探活——只是我用的是 Nginx 原生能力，没用 Lua 扩展。

**【思路与思考】**
这里要**先澄清"我用的是 Nginx"**——诚实但不露怯，然后展示你懂 Nginx/OpenResty 在架构里扮演的角色（反代 + LB + 健康检查 + 限流）。把 OpenResty 解释成"Nginx 的 Lua 增强版"就够了，别硬装用过。

**【👨‍💻追问】**
- **"OpenResty 的 Lua 能做什么 Nginx 原生做不到的？"** → 在请求处理任意阶段写业务逻辑，比如自定义鉴权、动态路由、灰度分流（按 header/比例）、限流算法自实现、聚合多个上游响应；原生 Nginx 只能靠配置，Lua 能写 if/循环。
- **"为什么大厂爱用 OpenResty？"** → 高并发场景下把一部分逻辑前移，扛量 + 减少后端压力，且 Lua 热加载不重启 worker。

## 第 7 题：OpenResty 要检查什么健康状态 ⚠️

**【话术】**
> 我认为健康检查要检查的是"这个节点到底能不能正常服务"，分三个层次：
> ① **TCP 层**：端口能连上（`tcpsock:connect`），证明进程活着；
> ② **HTTP 层**：请求应用自己的探活接口（如 `/health`）返回 `200`，证明 Spring 容器/请求链路正常；
> ③ **业务层**：更深一点可以检查依赖是否可用（数据库连接池、Redis 是否正常），甚至做一次只读查询，防止"应用活着但一查库就 500"的假健康。
> 我的 blog 对应：Nginx 探 `location /health`（HTTP 层），应用能返回 200 才算健康；因为 blog 依赖 MySQL/Redis/RabbitMQ，我理解的更严格做法是把中间件状态也放进健康响应里。

**【思路与思考】**
这题是第 2/3 题的"升维版"——把健康状态**分层**回答（TCP → HTTP → 业务），能体现架构思维。关键加分点是主动提出"**依赖检查**"（DB/Redis 挂了节点也不该接流量），这是很多背八股的人想不到的。

**【👨‍💻追问】**
- **"业务层健康检查会不会太重？"** → 会，探测请求也要走完整链路，高频探测会放大开销；所以业务层检查频率要低、只做轻量只读（比如 `SELECT 1`），或只在摘除/恢复时触发。
- **"健康响应要不要包含依赖状态？"** → 建议：`/health` 返回 `{"status":"UP","db":"UP","redis":"UP"}`，这样负载均衡只按总状态判断，运维能看明细。

## 第 8 题：三个负载挂掉了一个，数据面会发生什么 ⚠️

**【话术】**
> 我先解释"数据面"：在负载均衡语境里，控制面负责"决策"（发现故障、更新节点列表），数据面负责"转发"（实际把请求发给哪个后端）。挂掉一个节点后，数据面会发生：
> ① 健康检查先发现节点 down（控制面动作），把它从 upstream 可用列表**摘除**；
> ② 之后的数据面转发就只在**剩余健康节点**间轮询/加权分发，不再往故障节点发——所以用户侧基本无感知；
> ③ 正在转发到故障节点的**存量请求**会失败（连接重置/超时），Nginx 对这种失败默认直接返回 502，如果配了 `proxy_next_upstream` 会自动重试到下一个健康节点；
> ④ 挂了 1/3 的节点，单节点压力变大约 1.5 倍，如果原本接近容量上限就可能触发限流或雪崩。
> 我的 blog 是单节点所以没遇到这个场景，但 Nginx 的 upstream + `proxy_next_upstream` 重试机制我理解得很清楚。

**【思路与思考】**
这题考的是**控制面/数据面分离 + 故障转移**。答出"摘除 → 剩余节点接管 → 存量请求失败/重试 → 容量变化"这条时间线就完整了。能主动讲 `proxy_next_upstream` 重试和容量余量，说明你真懂运维。

**【👨‍💻追问】**
- **"重试会不会放大故障？"** → 会，A 挂了重试打到 B，B 也快挂了的话会把 B 打垮（级联）。所以要限制重试次数（默认 0，最多 1 次）、只对幂等请求重试（GET 可以，POST 要小心重复提交）。
- **"会话保持（sticky）的场景怎么办？"** → 挂掉的节点上所有用户会话失效，要么做会话共享（Redis 存 session/登录态，我 blog 的 JWT 天然无状态，正好规避这个问题），要么容忍重登。

## 第 9 题：恢复了，它又怎么检测到，有什么逻辑去检查 ⚠️

**【话术】**
> 节点恢复的检测靠**主动健康检查**（active check）：负载均衡会按固定周期（比如每 5s）持续对**已摘除节点**发探活请求（TCP 连接或 HTTP `/health`），一旦连续 N 次成功（比如 2~3 次），就判定恢复，把它重新加回可分发列表，新请求开始按权重分给它。
> 这个"连续成功/失败计数"是为了**防抖动**：一次成功不代表稳定，要连续几次通过才摘除/恢复，避免节点在 up/down 之间反复横跳（flapping）造成流量抖动。
> 对应我的 blog：Nginx 探 `/health`，如果当时挂了，探活会持续进行，恢复后 `/health` 重新返回 200，节点就能重新接流量；我没配多节点所以没实际触发过，但恢复检测的"周期探测 + 连续成功阈值 + 重新加入"这套逻辑是标准的。

**【思路与思考】**
这题是第 8 题的对称题，考**恢复检测逻辑**。答出三个要素：① 周期探测不停（对已摘节点持续探）② 连续成功阈值（防 flapping）③ 重新加入并恢复流量（可配小权重平滑放量）。这三要素就是健康检查的标准状态机（Health → Unhealthy → Health）。

**【👨‍💻追问】**
- **"探活是负载均衡主动还是后端上报？"** → 两种：主动探测（LB 定时去连）和被动检测（转发时发现连接失败就标记）；OpenResty/Nginx 主动探活要用 `nginx_upstream_check_module` 或 Lua 实现，Nginx 开源版默认只有被动失败标记。
- **"重新加入会不会把刚恢复的节点瞬间打爆？"** → 会，所以恢复后可以先给低权重/小流量，观察稳定再逐步调高。

## 第 11 题：策略模式适合什么场景 ✅

**【话术】**
> 策略模式的核心是"**同一件事有多种做法，运行时按条件选择，且互不影响**"，适合三类场景：
> ① **算法族可替换**：比如支付（微信/支付宝/银联）、排序算法、折扣计算——行为不同但调用方式一致；
> ② **消除大量 if/else**：一个方法里根据类型分支做不同处理，把每个分支抽成独立策略类，配合 `Map<类型, 策略>` 或 Spring 注入自动映射，扩展新策略不用改老代码（开闭原则）；
> ③ **可插拔、可热切换**：策略可以动态替换，不改调用方。
> 老实说，我 blog 项目里目前**没有用**策略模式——因为我的业务分支是"异步削峰/缓存三防"这种横切逻辑，不是"同一动作多算法"。但如果被问到我会举典型例子：比如我调 DeepSeek 生成摘要，如果未来接入多个模型厂商（DeepSeek/通义/Kimi），就会用策略模式：定义 `SummaryProvider` 接口 + 各厂商实现 + 按配置选择，这样切换模型不动业务代码。

**【思路与思考】**
这题是通用八股，面试官想听**你见过没用过也不怕**——诚实说"项目里没用"不可怕，可怕的是说用了但说不出代码。我的策略：① 讲清适用场景（算法族/if-else 重构/可插拔）② 诚实承认 blog 没用 ③ 立刻给一个"如果要用会怎么用"的具体设计（多模型摘要），证明你真的理解。

**【👨‍💻追问】**
- **"策略模式和状态模式、工厂模式区别？"** → 策略：行为算法可替换，客户端主动选；状态：行为随内部状态切换，客户端无感知；工厂：负责"创建对象"，解决"选哪个类"，策略解决"用哪个算法"，两者常搭配（工厂创建策略）。
- **"策略模式怎么避免 if-else 选择策略？"** → 用 Spring 注入成 `Map<String, Strategy>`（Bean 名当 key），或注解 + 扫描注册，调用时按 key 直接 get，天然去 if-else。
- **"Map 里 get 不到策略怎么办？"** → 加一个兜底默认策略（如默认支付方式），或启动时校验所有策略 Bean 是否齐全（fail-fast，符合我的工程原则）。

## 第 13 题：你这个分片，集群有多大 ⚠️

**【话术】**
> 诚实说：我的 blog 用的是**单机 MySQL + 单机 Redis**，没有做分片集群——因为博客场景数据量（文章、用户、评论）远没到单库瓶颈，单机 + 缓存 + 异步削峰就能扛住，我不会为了炫技引入分片的复杂度。
> 但我理解分片的原理：**水平分片**是把一张表按分片键（如 userId/articleId）哈希或范围拆分到多个库/节点，解决单库容量和写入瓶颈；分片后要解决**跨片查询、全局唯一 ID、分布式事务**三大难题。Redis 的集群（Cluster）则是把 16384 个槽位按哈希分到多主节点，解决单机内存和吞吐上限。
> 所以我的答案是：规模上"不需要分片"，能力上"我清楚分片是为了解决什么、会引入什么代价"。

**【思路与思考】**
这道题是"诱导你吹牛"的典型题——你项目里没做，硬吹分片集群就会被追问细节立刻露馅。最佳策略：**大方承认单机 + 解释为什么不需要（规模没到）+ 证明你懂分片原理和代价**。这种"知道何时不该用"的回答反而加分。

**【👨‍💻追问】**
- **"什么时候才需要分片？"** → 单库容量到上限、写入吞吐到瓶颈、或需要多机房部署；一般先做读写分离/缓存，还不够才分片。
- **"分片键怎么选？"** → 选查询最频繁的字段（避免跨片查询），如按 userId 分片后同用户数据都在一片，跨片查询尽量用"分片键 + 聚合"。
- **"分片后全局唯一 ID 怎么做？"** → 自增主键失效，用雪花算法 / UUID / Redis 发号器（我 blog 的分布式锁 value 就是用 UUID，道理类似）。

## 第 14 题：RAG 怎么切文档信息 ⚠️

**【话术】**
> 诚实说：我的 blog 做的是**大模型生成文章摘要**（调 DeepSeek API），不是完整 RAG，但我理解 RAG 的文档切分（chunking）逻辑。切分要考虑三个点：
> ① **切分粒度**：按语义/结构切，而不是纯按固定字符数硬切。常用的有：按段落/标题切（Markdown/PDF 结构）、按固定长度 + 重叠窗口切（chunk_size=500 + overlap=50，避免语义被截断在边界）、按句子/句子对切；
> ② **保留上下文**：切分要带 overlap 重叠，防止一个完整语义（如一段话的后半句）被切到两个 chunk 里导致检索时语义断裂；
> ③ **索引元数据**：每个 chunk 要保留来源（文档 ID、章节号、页码），便于召回后溯源和做过滤。
> 对应我的理解：我的摘要功能本质是"整篇喂给模型"，而 RAG 是"先切片检索再拼装喂给模型"，区别在于前者一次处理、后者需要切分 + 向量化 + 召回。

**【思路与思考】**
RAG 在 blog 里确实没有，但你简历写了 AI 相关，面试官会追问。策略：**承认没做 RAG + 一句话点出本质区别（切分→向量化→召回→拼装）+ 讲清切分的关键决策点（粒度/重叠/元数据）**。把话头引回"我实际做了 DeepSeek 摘要"。

**【👨‍💻追问】**
- **"chunk_size 怎么定？overlap 多少？"** → 取决于模型上下文和语义单元，一般 300~800 字符、overlap 10%~20%；太小语义不完整、太大召回精度下降且浪费 token。
- **"切分切错了怎么办？"** → 见第 15 题。

## 第 15 题：切割之后发现不对，还有什么后续处理方式 ⚠️

**【话术】**
> 我理解切分（chunking）是 RAG 效果的地基，切错了要靠"**召回侧和生成侧双重补救**"：
> ① **召回侧**：调整切分策略本身——改用结构化切分（按标题/段落）、调大 overlap、用语义切分（embeddings 计算句子相似度，相似才归一个 chunk，而不是固定长度）；
> ② **混合检索**：向量检索 + 关键词检索（BM25）双路召回再融合，弥补纯向量对精确词/专业术语召回弱的问题；
> ③ **重排（Rerank）**：召回的 top-K 先用粗粒度，再用 rerank 模型精排，把真正相关的 chunk 提到前面，过滤无关片段；
> ④ **生成侧兜底**：提示词里让模型"只能基于给定片段回答，找不到就明说不知道"，并给出引用来源，防止模型拿错误片段硬编。
> 对应我的理解：这就像我 blog 里布隆过滤器误判后的"空值缓存兜底"思路——**主方案 + 兜底方案双层设计**，主方案保证大多数场景，兜底保证不崩。

**【思路与思考】**
这题考"工程兜底思维"。答出"召回侧调优 + 混合检索 + Rerank + 生成侧约束"四层就完整了。最后类比 blog 的"主方案+兜底"，把不熟的 RAG 又拉回你熟的缓存体系，一举两得。

**【👨‍💻追问】**
- **"怎么评估切分好不好？"** → 用召回率/准确率 + 端到端回答质量评估，人工看 badcase；常见指标有 Recall@K、命中率。
- **"Rerank 会不会增加太多延迟？"** → 会，所以只对 top-K（如 20）精排到 top-5，控制计算量。
