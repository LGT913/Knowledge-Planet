## 三、安全与认证

### 问题 5：为什么用 BCrypt 而不是 MD5？

**问题本身**：
> 问：你项目里密码是怎么加密的？为什么不用 MD5？
> 追问：BCrypt 和 MD5 有什么本质区别？
> 再追问：BCrypt 为什么自带盐值就安全？

**为什么要这么做**：
- MD5 运算太快，抗暴力破解能力差，且不自带盐值，容易被彩虹表攻破
- BCrypt 运算速度可调（工作因子），自带盐值，每次加密结果不同，彩虹表失效

**具体怎么做**：

| 对比项 | MD5 | BCrypt |
|--------|-----|--------|
| 运算速度 | 极快（CPU每秒几亿次） | 可调慢（几百毫秒） |
| 盐值 | 需手动加盐 | 自带盐值 |
| 彩虹表 | 易被攻破 | 盐值不同，失效 |
| 暴力破解 | 成本低 | 成本极高 |

**项目实战**：
- 注册时 `PasswordEncoder.encode(password)` 加密入库
- 登录时 `PasswordEncoder.matches(password, user.getPassword())` 验证
- 使用 `spring-boot-starter-security` 提供的 BCrypt

**如何验证**：
1. 注册两个相同密码的用户，查看数据库中密码是否不同（盐值不同）
2. 登录时用正确密码验证成功，错误密码验证失败
3. 查看加密后的密码格式（BCrypt 密码以 `$2a$` 开头）

### 问题 6：Session 和 JWT 有什么区别？

**问题本身**：
> 问：你项目里是怎么管理用户登录状态的？为什么不用 JWT？

**为什么要这么做**：
- Session 适合单体架构，简单便捷
- JWT 适合分布式/微服务架构，无状态，扩展性好

**具体怎么做**：

| 对比项 | Session | JWT |
|--------|---------|-----|
| 存储位置 | 服务端 | 客户端（Token） |
| 适用架构 | 单体 | 分布式/微服务 |
| 扩展性 | 难（需Session共享） | 易（无状态） |

**项目实战**：
- 项目用 HttpSession，单体架构足够
- 如果后续做分布式部署，会切换到 JWT

**如何验证**：
1. 登录成功后，查看浏览器 Cookie 中是否有 JSESSIONID
2. 关闭浏览器重新打开，验证是否需要重新登录（Session 过期）
3. 在不同浏览器登录同一账号，验证互不影响（Session 隔离）

### 问题 7：登录成功后直接返回 User 对象有什么安全问题？

**问题本身**：
> 问：你登录接口返回什么数据给前端？
> 追问：直接返回 User 对象会不会暴露敏感信息？
> 再追问：怎么避免密码、手机号这些字段被返回？

**为什么要这么做**：
- 即使密码是加密的，也不应该暴露给前端
- 手机号属于个人隐私，不应返回给前端
- 需要用 VO（视图对象）过滤敏感字段

**具体怎么做**：
1. 创建 UserVO 类，只包含需要返回的字段（id、username、role、roleName、statusName）
2. 登录成功后，将 User 对象转换为 UserVO 对象返回
3. 项目已有 `convertToUserVO()` 方法，但登录接口未使用，需优化

**项目实战**：
- 当前登录接口直接返回 User 对象，存在安全隐患
- 需优化为返回 UserVO，过滤 password、phone 等敏感字段

**如何验证**：
1. 登录成功后，查看返回的 JSON 是否包含 password、phone 字段
2. 优化后重新登录，确认敏感字段不再返回
3. 验证 roleName、statusName 等业务字段正常返回
