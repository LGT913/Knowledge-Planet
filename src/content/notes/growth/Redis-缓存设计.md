## 6. Redis 缓存设计

> 任职要求明确要求"熟练掌握 redis 等缓存技术"，项目未实际使用但必须能说出理论+可应用场景。

### 6.1 旁路缓存模式（Cache-Aside）

**读取流程**：
```
1. 查 Redis：GET article:{id}
2. 命中 → 直接返回
3. 未命中 → 查 DB → SET article:{id} (过期时间30分钟) → 返回
```

**更新流程**：
```
1. 先更新数据库
2. 再删除缓存（不是更新缓存！）
```

⚠️ **为什么删除不是更新**：删除幂等性好，不存在并发写缓存导致的一致性问题。

**项目中可应用 Redis 的场景**：

| 场景 | 缓存 key | 缓存值 | 过期时间 | 理由 |
|------|---------|--------|---------|------|
| 系统配置 | config:{key} | config_value | 1小时 | 读取频繁，极少修改 |
| 登录状态 | session:{userId} | User 对象 | 30分钟 | 替代 HttpSession，支持分布式 |
| 统计数据 | stats:today_orders | COUNT 结果 | 5分钟 | 不需要实时精确 |
| 代取员信息 | proxy:{userId} | ProxyUser 对象 | 10分钟 | 查任务列表时频繁读取 |

### 6.2 缓存删除失败兜底（⚠️ 连环追问）

**问：数据库更新成功但删除 Redis 缓存失败，怎么兜底？**

**推荐方案（重试 + 过期时间）**：
```java
int retry = 3;
while (retry > 0) {
    try { redisTemplate.delete(key); break; }
    catch (Exception e) { retry--; Thread.sleep(100); }
}
// 过期时间兜底：即使删除失败，过期后也会自动失效
redisTemplate.opsForValue().set(key, article, 30, TimeUnit.MINUTES);
```

**为什么不选 MQ**：博客/配置类系统对一致性要求不高，引入 MQ 增加复杂度。电商等强一致性场景才需要。

**其他方案对比**：

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| 同步重试+过期时间 | 简单直接 | 重试阻塞线程 | 一致性要求不高 |
| 延迟双删 | 处理竞态条件 | 延迟时间不好定 | 读多写少 |
| MQ异步补偿 | 解耦不阻塞 | 增加系统复杂度 | 强一致性 |
| 过期时间兜底 | 最终一定一致 | 过期前不一致 | 所有场景必加 |

### 6.3 缓存穿透、击穿、雪崩

| 问题 | 现象 | 应对 |
|------|------|------|
| 穿透 | 查不存在的数据，每次直达 DB | 缓存空值（短过期5分钟）+ Controller 参数校验 |
| ⚠️ 击穿 | 热点 key 过期瞬间，大量请求打到 DB | 互斥锁（只一个请求查 DB 写缓存）+ 热点数据永不过期 |
| 雪崩 | 大量 key 同时过期 | 过期时间加随机值 + 多级缓存 |
