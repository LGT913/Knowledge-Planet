## 四、Redis 缓存

### 1. 基础（⭐⭐⭐⭐⭐）

**Redis 为什么快？**

1. 纯内存操作
2. 单线程模型（避免线程切换和锁竞争）
3. IO 多路复用（epoll）
4. 高效的数据结构

**Redis 五大基本类型**

| 类型 | 应用场景 |
|------|----------|
| String | 缓存、计数器、分布式锁 |
| List | 消息队列、排行榜 |
| Hash | 对象、用户信息 |
| Set | 去重、交集并集差集（共同好友） |
| ZSet（有序集合） | 排行榜、带权重的队列 |

**Redis 持久化**

| 方式 | RDB | AOF |
|------|-----|-----|
| 原理 | 快照，某个时间点的数据 | 追加写命令 |
| 文件大小 | 小 | 大 |
| 恢复速度 | 快 | 慢 |
| 数据安全性 | 丢数据多 | 丢数据少 |
| 默认 | 开启 | 关闭 |
| 配置 | save 900 1 | appendonly yes |

**Redis 4.0 + 混合持久化**：AOF 文件开头是 RDB 格式，后面追加命令，兼顾速度和安全。

### 2. 缓存三大问题（⭐⭐⭐⭐⭐ 项目必问）

**缓存穿透**

- 问题：查询一个数据库和缓存都没有的数据，请求直接打到数据库
- 解决：
  1. 布隆过滤器（预判数据是否存在）
  2. 缓存空值（设置短过期时间）

**缓存击穿**

- 问题：某个热点 key 过期的瞬间，大量请求同时打到数据库
- 解决：
  1. 互斥锁（setnx）
  2. 热点数据永不过期

**缓存雪崩**

- 问题：大量 key 同时过期，或 Redis 挂了，请求全部打到数据库
- 解决：
  1. 过期时间加随机值
  2. 多级缓存
  3. Redis 集群（哨兵/集群模式）
  4. 服务熔断降级

### 3. 缓存一致性（⭐⭐⭐⭐⭐）

**先更数据库还是先删缓存？**

推荐：**先更新数据库，再删除缓存**

原因：
- 先删缓存的话，删完缓存还没更数据库时，有读请求把旧数据写回缓存，就脏了
- 先更数据库再删缓存，虽然也有极小概率脏数据（并发场景），但概率低很多

**进阶：延时双删**

1. 先删缓存
2. 更数据库
3. 休眠一会（比如 500ms）
4. 再删一次缓存

**Canal 监听 binlog 异步更新缓存**（进阶方案，能答出来很加分）

### 4. 分布式锁（⭐⭐⭐⭐）

**Redis 实现分布式锁**

- `set key value nx ex 30`（原子操作，加锁+设过期时间）
- value 用唯一标识（比如 UUID），解锁时判断是不是自己加的锁
- 解锁用 Lua 脚本保证原子性

**锁续期**：看门狗机制（Redisson 实现）

**RedLock**：多节点实现，防止单点故障

### 5. 其他

**Redis 内存淘汰策略**

1. `noeviction`：不淘汰，写入报错（默认）
2. `allkeys-lru`：所有 key 中，淘汰最近最少使用
3. `volatile-lru`：有过期时间的 key 中，淘汰最近最少使用
4. `allkeys-random`：所有 key 随机淘汰
5. `volatile-random`：有过期时间的随机淘汰
6. `volatile-ttl`：快过期的先淘汰

**Redis 和 Memcached 区别**

| 对比项 | Redis | Memcached |
|--------|-------|-----------|
| 数据类型 | 5种+ | 只有 String |
| 持久化 | 支持 | 不支持 |
| 价值 | 大（1G） | 小（1M） |
| 线程模型 | 单线程 | 多线程 |
