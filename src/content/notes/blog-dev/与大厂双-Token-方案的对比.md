## 与大厂双 Token 方案的对比

### 大厂双 Token 方案简介

```
┌─────────────────────────────────────────────────────────────────┐
│                    双 Token 体系                                  │
│                                                                  │
│  Access Token（短期）          Refresh Token（长期）              │
│  ┌──────────────────┐        ┌──────────────────┐               │
│  │ 有效期：15-30 分钟 │        │ 有效期：7-30 天   │               │
│  │ 存储：前端内存     │        │ 存储：前端         │               │
│  │ 作用：鉴权        │        │  localStorage      │               │
│  │ 风险：泄露影响小  │        │ 作用：换取新       │               │
│  │ 刷新：自动静默    │        │       Access Token  │               │
│  └──────────────────┘        │ 风险：泄露影响大    │               │
│                               └──────────────────┘               │
│                                                                  │
│  访问流程：                                                       │
│  1. 请求带 Access Token                                          │
│  2. 签名有效 → 放行                                               │
│  3. 签名过期 → 前端自动用 Refresh Token 换新 Access Token         │
│  4. 换 Token 时服务端校验 Refresh Token 是否在黑名单中             │
└─────────────────────────────────────────────────────────────────┘
```

### 对比分析

| 维度 | 本项目方案（单 Token + Redis 黑名单） | 大厂双 Token 方案 |
|------|--------------------------------------|-------------------|
| **Token 数量** | 1 个 Token | 2 个 Token（Access + Refresh） |
| **Access Token 有效期** | 24 小时（较长） | 15-30 分钟（极短） |
| **Token 泄露风险** | 泄露后 24 小时内可用 | 泄露后 15-30 分钟内可用 |
| **踢人延迟** | 实时（下一请求即生效） | 实时（下一请求即生效） |
| **登出能力** | ✅ 支持（黑名单） | ✅ 支持（黑名单） |
| **黑名单存储** | 每个 Token 一条 jti 黑名单 | 每个 Refresh Token 一条黑名单 |
| **黑名单数量** | 24h 内登出的 Token 数量 | 30 天内登出的 Refresh Token 数量 |
| **服务器压力** | 每次请求 2 次 Redis 查询 | 每次请求 1 次 Redis + 每 15-30 分钟 1 次刷新 |
| **实现复杂度** | 低（1 个 Token，逻辑简单） | 高（双 Token 换发逻辑、并发控制） |

### 为什么本项目选择单 Token 方案？

| 项目特点 | 结论 |
|---------|------|
| 博客项目，非金融/支付场景 | Token 泄露 24 小时的风险可接受 |
| 低并发，用户量不大 | 黑名单数量可控，不需要换发机制降低 Redis 压力 |
| 作者维护，无需前端团队配合 | 单 Token 前端逻辑简单，不需要处理静默刷新 |
| 后端无手机号/多设备管理 | 不需要考虑多设备同时刷新 Token 的并发问题 |

### 如果面试官问"为什么不升级双 Token"

**回答模板**：

> 我们项目当前是博客系统，Token 生命周期 24 小时，泄露风险可控。单 Token + Redis 黑名单方案已经覆盖了所有踢下线场景（登出、踢人），且后端复杂度最低。
>
> 如果未来业务升级到需要更高安全性（如支付、金融、社交），我会升级到双 Token 方案：
> 1. Access Token 15 分钟过期，降低泄露影响面
> 2. Refresh Token 7 天，配合 Redis 黑名单做踢人
> 3. 前端增加 axios 拦截器自动刷新 Token
>
> 但双 Token 方案也有代价：Refresh Token 的黑名单需要存 7-30 天，Redis 内存占用比单 Token 方案大 10-100 倍，且前端需要处理 Token 刷新期间的并发请求（多个请求同时过期时，不能让它们都去刷新 Token，要加锁排队）。这个复杂度在我们当前阶段是不必要的。

## 最终架构图

```
┌─────────────────────────────────────────────────────────────────┐
│                    完整鉴权链路                                    │
│                                                                  │
│  用户登录 ──► JwtUtil.generateToken(userId, role)                │
│                   └─ jti = UUID.randomUUID()                     │
│                   └─ 签名 + 过期时间 = 24h                        │
│                                                                  │
│  每次请求 ──► JwtAuthenticationFilter.doFilterInternal()         │
│                   ├─ ① Bearer 前缀处理                            │
│                   ├─ ② jwtUtil.validateToken（签名 + 过期）       │
│                   ├─ ③ 黑名单检查 hasKey(blacklist:{jti})        │
│                   ├─ ④ 禁用检查 hasKey(disabled:{userId})         │
│                   │      └─ Redis 宕机 → 降级查 DB               │
│                   └─ ⑤ 设置 SecurityContext → 放行               │
│                                                                  │
│  用户登出 ──► redisUtil.set(blacklist:{jti}, TTL=剩余时间)        │
│                                                                  │
│  管理员踢人 ──► DB: enabled=false + Redis: SET disabled:{id}     │
│                                                                  │
│  项目启动 ──► DisabledUserLoader: DB → Redis 恢复禁用列表         │
└─────────────────────────────────────────────────────────────────┘
```
