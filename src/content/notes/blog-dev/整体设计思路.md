## 一、整体设计思路

### 1.1 为什么需要 WebSocket？

博客评论功能的问题：用户 A 对文章发表评论后，文章作者 B 和其他读者 C 无法实时看到新评论，必须手动刷新页面。引入 WebSocket 后，任何在文章详情页的用户都能实时收到新评论通知。

### 1.2 为什么用 RabbitMQ + WebSocket 组合？

**问题分析：**

| 方案 | 问题 |
|---|---|
| 评论接口直接 WebSocket 推送 | 推送失败会拖慢接口响应，用户体验差 |
| 评论接口直接 WebSocket 推送 | 推送逻辑与业务逻辑耦合，不符合单一职责原则 |

**最终架构：**

```
用户发评论 → CommentServiceImpl.createComment()
                ├── ① 写 MySQL（同步，事务内）
                ├── ② 删 Redis 缓存（同步，事务内）
                └── ③ 发 RabbitMQ 消息（异步，失败不影响主流程）
                        → CommentNotifyConsumer.handleCommentNotify()
                            ├── ④ SETNX 幂等去重（Redis）
                            └── ⑤ SimpMessagingTemplate.convertAndSend()
                                    → STOMP Broker → /topic/article/{articleId}/comments
                                            → ⑥ 前端 SockJS 收到消息 → Toast 通知
```

**设计要点：**

| 步骤 | 设计决策 | 原因 |
|---|---|---|
| ③ RabbitMQ 异步 | 解耦推送与业务 | 消息发送失败不影响评论创建，接口响应不阻塞 |
| ④ SETNX 幂等去重 | 防止重复推送 | RabbitMQ 可能因网络抖动重发消息 |
| ⑤ STOMP Topic 广播 | 一对多推送 | 文章详情页所有用户（作者+读者）都能看到 |
| ⑥ SockJS 兜底 | 兼容旧浏览器 | 不支持 WebSocket 的环境自动降级为长轮询 |

### 1.3 推送目标选择：Topic vs Queue

| 对比 | /topic/article/{articleId}/comments | /queue/user/{authorId}/notify |
|---|---|---|
| 推送方式 | 广播（一对多） | 点对点（一对一） |
| 谁收到 | 文章详情页所有用户 | 只有文章作者 |
| 适用场景 | 文章评论区实时更新 | 作者专属通知栏 |
| 本项目选择 | **是** | 后续扩展 |

结论：选择 `/topic` 广播模式，让所有在文章详情页的用户都能看到新评论，体验更好。

## 二、具体步骤与核心代码

### 2.1 添加 WebSocket 依赖

**文件：** `blog/pom.xml`

**改动：** 在 `spring-boot-starter-amqp` 下方插入：

```xml
<!-- WebSocket（STOMP 协议，实时推送） -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-websocket</artifactId>
</dependency>
```

**设计思路：**

- `spring-boot-starter-websocket` 包含 Spring WebSocket、STOMP 支持、SockJS 降级方案
- 无需额外引入 SockJS 服务端依赖，Spring Boot 已内置
- 版本由 `spring-boot-starter-parent` 统一管理，避免版本冲突
