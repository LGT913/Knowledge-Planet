├── deleteByPattern("article:list:page:*")     → 删除所有分页缓存（含分类）

### 二、缓存穿透问题（Cache Penetration）

#### 问题 1：`getArticle` 未缓存空值

```java
Article article = articleRepository.findById(id)
        .orElseThrow(() -> new RuntimeException("文章不存在"));
```

**原因**：当文章 ID 不存在时，直接抛异常返回，**没有缓存空值**。攻击者用不同无效 ID 反复请求，每次都打到数据库。

**解决思路**：查不到文章时，缓存一个空标记值（如空字符串 `"NULL"` 或特殊对象），设置短 TTL（如 60s）。下次查询命中空标记直接返回，不查库。

#### 问题 2：`getAllArticles`、`getArticleRankingByViews`、`getArticleRankingByLatest` 均无穿透防护

**原因**：这三个方法查到空列表后直接返回，没有缓存空值。虽然正常场景下不太可能为空（总有文章），但防御性编程应该覆盖。

**解决思路**：与 `getAllArticlesPage` 第124-128行的做法一致，查到空结果时缓存空列表 + 短 TTL。

#### 问题 3：`getAllArticlesPage` 的空值缓存判断存在隐患

```java
if (cacheObj instanceof List && totalObj instanceof Number) {
```

**原因**：当缓存了空列表（`Collections.emptyList()`）和 `0L` 后，这个条件会命中，返回空列表——逻辑上正确。但问题在于：**无法区分"缓存了空值"和"正常空页"**。如果之后新增了文章，空值缓存未失效（见下方 Bug 2），用户会持续看到空列表。

**解决思路**：空值缓存的 key 加特殊后缀（如 `:empty`），或缓存一个标记对象区分空值缓存和正常数据。



### 三、缓存击穿问题（Cache Breakdown）

#### 问题 4：`getArticle` 分布式锁实现有多个缺陷

**缺陷 4a：锁释放不安全**

`redisUtil.delete(lockKey)` 直接删除锁，**没有校验锁的持有者**。如果锁已超时（3秒）被其他线程获取，当前线程会误删别人的锁。

**解决思路**：锁的 value 存入唯一标识（如 UUID），释放时用 Lua 脚本判断 value 匹配后再删除。

**缺陷 4b：锁超时时间过短**

`Duration.ofSeconds(3)` ——3 秒。如果数据库查询慢或网络抖动，锁可能提前过期，导致第二个线程进入临界区。

**解决思路**：适当延长至 10-15 秒，或引入锁续期机制（看门狗）。

**缺陷 4c：重试 3 次后直接查数据库**

重试失败后直接查库，击穿防护形同虚设。高并发下锁超时会导致大量请求同时走到这里。

**解决思路**：重试失败后返回降级数据（如缓存旧值、默认提示），而非直接打数据库。

#### 问题 5：`getAllArticlesPage` 等热查询方法无击穿防护

**原因**：分页列表是高频访问的热点数据，缓存过期瞬间如果有大量并发请求，会同时查库。`getArticle` 加了锁，但 `getAllArticlesPage` 没有加。

**解决思路**：对热点 key 采用同样的分布式锁 + 二次检查模式，或考虑使用逻辑过期方案（缓存永不过期，value 中带过期时间戳，后台异步刷新）。



### 四、缓存雪崩问题（Cache Avalanche）

#### 问题 6：随机 TTL 应用不一致

**原因**：三个方法使用固定 TTL，同时过期会导致雪崩。

**解决思路**：所有缓存写入统一加随机偏移（基础 TTL ± 10%~30%）。

#### 问题 7：静态 `RANDOM` 声明了但未使用

**位置**：声明了 `static final RANDOM`，但都用了 `new java.util.Random()`。

**原因**：每次调用创建新 Random 对象，浪费内存。已有静态变量却不用。

**解决思路**：统一使用静态 `RANDOM`。



### 五、缓存一致性问题（最严重的业务 Bug）

#### Bug 2：`clearRelatedCaches` 未清理分类相关缓存

```java
for (int i = 0; i < 10; i++) {
    redisUtil.delete(ARTICLE_LIST_PAGE_KEY + i);  // 只删 article:list:page:0 ~ 9
}
redisUtil.delete(ARTICLE_TOTAL_COUNT_KEY);  // 只删全局总数
```

**原因**：问题2修复后，分类分页的缓存 key 是 `article:list:page:0:cat:1`、`article:total:count:cat:1` 等格式。但 `clearRelatedCaches` **只删除了不带分类后缀的 key**，分类相关缓存完全不会被清理。

**后果**：

- 新建文章后，该分类的文章列表缓存不失效，用户看不到新文章
- 删除文章后，该分类的文章列表仍显示已删除的文章
- 修改文章分类后，旧分类和新分类的缓存都不更新

**解决思路**：

- 方案 A：用 `redisTemplate.keys("article:list:page:*")` 模糊匹配删除所有分页缓存（需确保 RedisUtil 支持）
- 方案 B：在 `RedisUtil` 中新增 `deleteByPattern` 方法，使用 `SCAN + DELETE` 避免阻塞
- 方案 C：维护一个分类列表，遍历所有分类组合 key 删除

------

#### Bug 3：`clearRelatedCaches` 只清理前 10 页

**原因**：`for (int i = 0; i < 10; i++)` 硬编码 10 页。如果文章超过 100 篇（10页 × 10条/页），第 10 页及以后的缓存不会被清理。

**解决思路**：同 Bug 2，用模糊匹配删除所有分页缓存。
