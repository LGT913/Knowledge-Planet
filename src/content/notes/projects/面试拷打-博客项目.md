## 一、项目开场白 / 全局架构

### Q：简单介绍下你的博客项目

**话术：**
> 这是一个从 0 到 1 全栈实现的个人博客系统，分**单体版**和**微服务演进版**两套。
> 单体版：Spring Boot + MySQL + Redis + Redisson + RabbitMQ + WebSocket + JWT，已完整部署上阿里云 ECS（Docker Compose 中间件 + Nginx 反代 + systemd 常驻）。
> 微服务版：按业务边界拆成 user-service、article-service，用 Nacos 注册/配置中心 + Gateway 网关 + OpenFeign 服务调用 + Sentinel 限流。
> 核心难点不是 CRUD，而是围绕**文章详情的高频读**和**阅读量/点赞的高频写**做了缓存三防、异步削峰、消息解耦三层设计。

**👨‍💻追问：为什么做两套？单体没价值吗？**
> 单体能上线、能完整走通全链路，体现我"能交付落地"的能力，也验证了缓存/锁这些核心设计。微服务版是我为了**验证架构演进能力**做的，不是重复造轮子——同样的业务，单体用一个事务搞定，微服务用 Feign 跨服务调用实现，这种"演进"过程才最体现对分布式利弊的理解。

### Q：画出你的架构图 / 请求是怎么贯穿全链路的

**话术：**
> 一条请求链路：浏览器 → Nginx（静态资源 + 反代 /api、/ws）→ Spring Security 过滤器链（JWT 校验）→ Controller → Service（先查布隆过滤器 → 查缓存 → 未命中走分布式锁回源 DB）→ 返回统一 Result。
> 写操作部分：文章创建 → 发送摘要生成消息进 RabbitMQ → SummaryConsumer 幂等检查 + 限流 → 调 DeepSeek → 写库 → 失效缓存。阅读量 → Redis INCR + 脏标记 → 定时批量落库。

## 二、Java 基础 / 集合 / 并发

### Q：你项目里用了那么多并发方案，为什么不直接用 synchronized？

**话术：**
> 因为 my 并发的场景都在**跨实例的 Redis 层**。synchronized 锁的是单 JVM 的 monitor，只能管一台机器内的线程互斥，解决不了多实例部署时的竞争。而计数我用 Redis INCR 原子自增、防击穿用 Redisson 分布式锁、幂等用 setIfAbsent，这些都是**锁在 Redis 上、所有实例共享同一把**，才是分布式场景的正确解。synchronized 只适合单 JVM 内存级的轻量互斥，我那些 Bean 都是无状态的，没这个需求。

**👨‍💻追问：i++ 为什么不安全？**
> `i++` 在字节码是"读 → 改 → 写"三步，非原子。多线程同时读同一变量再各自 +1 写回，会互相覆盖（丢失更新）。`AtomicInteger` 用 `CAS` 保证了一步到位；但跨进程到 Redis 就是 `INCR` 原子指令，同理。

### Q：HashMap 线程安全吗？你什么场合怎么规避？

**话术：**
> HashMap 在多线程并发 put 时 JDK1.7 可能头插法成环导致死循环，1.8 改尾插后主要问题是数据丢失/CAS 失败的无必要调用，且不是线程安全。我项目里没有用 HashMap 做共享可变缓存，跨实例的缓存都放 Redis，单机内的缓存重建状态用的是池里的局部变量，所以没踩这个坑。真要并发场景会用 ConcurrentHashMap（分段锁/CAS）。

**👨‍💻追问：ConcurrentHashMap 1.7 和 1.8 区别？**
> 1.7 分段锁 Segment（继承 ReentrantLock），分段粒度粗；1.8 放弃分段，改为 `Node` 数组 + 链表 + 红黑树，锁粒度细到"头节点"，用 `synchronized + CAS`，支持并发扩容。性能比 1.7 好。

## 三、JVM 与调优

### Q：你项目做过 JVM 调优吗？

**话术：**
> 老实说，我的博客是单机小流量，只做了最基础的**堆内存设置**：`-Xms256m -Xmx512m`，防止 OOM 打崩单机。没有做复杂的 GC 调优——因为单机低流量场景，盲目上 G1 参数/堆比例只是炫技，面试官一问为什么调就说不上来。
> 但我系统学过 JVM：内存模型（堆/栈/元空间/方法区）、GC 算法（复制/标记清除/标记整理）、常用收集器（G1 的 Region + 混回收、ZGC 的低停顿）、以及 jstat/jmap/jstack/arthas 排查工具。我清楚调优的**触发场景**（GC 频繁 STW、内存泄漏、吞吐不足），而不是堆参数。

**👨‍💻追问：什么时候才需要真调优？OOM 你怎么排查？**
> 线上 YGC 频繁导致 CPU 飙升、Full GC 引起长时间 STW、或者内存持续增长不下降（疑似泄漏）时才需要。OOM 排查：① 先开 `-XX:+HeapDumpOnOutOfMemoryError` 保留现场 → ② `jmap -dump` 导 dump → ③ MAT/VisualVM 查支配树找大对象 → ④ 看是堆内存泄漏（该回收没回收，查强引用/静态集合）还是内存溢出（确实不够，扩堆或改结构）。

## 四、Spring Boot 与容器

### Q：为什么你们用构造器注入而不是 @Autowired 字段注入？

**话术：**
> 注入方式本身**不影响线程安全**——注入的都是无状态单例。但构造器注入有三个生产价值：① 字段可以 `final`，依赖不可变、反射安全；② 便于单测，构造器显式传入 mock 就能替换依赖；③ 能**尽早暴露循环依赖**——字段注入能"逃过"启动期检查，到实际调用才炸；构造器注入启动时直接报告循环依赖失败。所以我用 `@RequiredArgsConstructor` 配合 final 字段。

**👨‍💻追问：Spring 解决循环依赖的机制是什么？构造器注入为什么解决不了？**
> Spring 用**三级缓存**解决 setter/字段注入的循环依赖：一级存成品、二级存提前暴露的 Bean、三级存 `ObjectFactory` 工厂。A 依赖 B、B 依赖 A 时，A 建到一半先通过三级缓存暴露一个**提前代理**给 B 用，B 完成后再回来填 A。但**构造器注入发生在对象创建阶段**，此时还没放进三级缓存，无法提前暴露，所以构造器循环依赖直接报错。这也是构造器注入"严格、尽早失败"的体现。

### Q：为什么选 Spring Boot 4.x？和 3.x 有啥区别？

**话术：**
> 用新版本一方面验证自己对新技术的跟踪能力，另一方面 Spring Boot 4 基于 Jakarta EE、要求 JDK 17+，并强化了可观测性（Micrometer）和 GraalVM 原生支持。我项目是 JDK17 + Spring Boot 4.0.6。我会说明版本演进踩过的坑——比如 4.x 里 `@Modifying` 查询的事务要求更严格，以及 Redisson 与 Boot 4 的 RedisProperties 类路径冲突需要排除自动装配、手动建 Bean。

## 五、Spring Security + JWT 认证

### Q：登录流程讲讲，JWT 存在哪？

**话术：**
> 流程：用户 POST /api/auth/login → 校验账号密码（BCrypt 比对）→ 签发 JWT（含 userId、username、role、过期时间，用环境变量注入的密钥签名）→ 返回给前端。前端把 token **存 localStorage**，后续每个请求由 axios 拦截器自动加 `Authorization: Bearer <token>` 头。
> 后端每次请求经 `JwtAuthenticationFilter` 拦截：解析 token → 校验签名和过期 → 从 Redis 查账号是否被禁用 → 封装 UserPrincipal 放入 SecurityContext，后面用 `@AuthenticationPrincipal` 取当前用户，`@PreAuthorize("hasRole('ADMIN')")` 做 RBAC 权限校验。

**👨‍💻追问：JWT 存 localStorage 有 XSS 风险，你有防护吗？**
> 这是 JWT 方案的经典权衡。存 Cookie（HttpOnly）防 XSS 但不防 CSRF，且跨域/移动端不友好；存 localStorage 方便但怕 XSS。我的防护侧重：① 前端实际是 Vue，框架默认转义，降低 XSS 面；② 在后端对 HTML/脚本做转义和过滤（XSS 拦截）；③ JWT 采用短过期（24h），降泄漏损失。同时我说明了纯 JWT 的无状态在"主动踢人/禁用"上的短板，所以我用 **Redis 记住禁用账号**来弥补"改库不生效"的问题——这是结合 DB 数据真相源 + Redis 加速缓存的折中方案。

**👨‍💻追问：token 被偷了怎么踢人？服务端能主动下线吗？**
> 纯 JWT 无状态就踢不掉，所以我不做成"纯无状态"。我维护了账号 `enabled` 字段（DB 真源），并在 Redis 存禁用标记。JwtAuthenticationFilter 每请求会查 Redis 禁用标记，命中就直接清掉 SecurityContext、拒绝访问——相当于实现了**服务端可按 user 维度快速封禁**。真正的"踢人"还可用 token 版本号/黑名单实现，我理解原理。

### Q：为什么用 OncePerRequestFilter 而不是 Maven Interceptor 做 JWT 校验？

**话术：**
> 因为要并入 Spring Security 的过滤器链，让鉴权结果进入 SecurityContext、被 `@PreAuthorize` 和 `SecurityContextHolder` 统一管理。MVC Interceptor 是**独立于 Security 的旁路**，会造成路径规则重复维护、SecurityContext 不统一。我在 `JwtAuthenticationFilter` 里 `OncePerRequestFilter` 保证一次请求只跑一次，且在 `UsernamePasswordAuthenticationFilter` **之前**执行，让匿名/已认证状态在进入业务前就绪。

**👨‍💻追问：SecurityContext 为什么要 clear？**
> 因为 Tomcat 的线程是**复用的**，如果上一次请求清理不干净，下一次请求可能"继承"到上一个用户的安全上下文，造成**越权/串号**。所以处理完（尤其 token 非法时）必须 `SecurityContextHolder.clearContext()`，防止线程池污染。

## 六、MySQL 数据库

### Q：你项目里哪些表、哪些字段加了索引？

**话术：**
> 文章表 article 的 `categoryId`、`userId` 加了普通索引（因为按分类/作者查询是高频）；`createTime` 参与列表排序，建了索引支撑 `ORDER BY createTime DESC` 的分页；主键 id 用自增。
> Repository 里用 `findAllByOrderByCreateTimeDesc`、`findByCategoryIdOrderByCreateTimeDesc` 这种**方法名定排序**的方式，让 JPA 生成稳定、可预期的 SQL。

**👨‍💻追问：为什么主键用自增而不是 UUID？**
> 自增主键是**聚簇索引**，插入时数据按顺序追加到 B+ 树末尾，页不用频繁分裂，**插入性能好、碎片少**。UUID 随机分布会让 B+ 树频繁分裂重排，写放大严重，索引占用空间也大。单库场景自增是正确选择；只有分库分表/防枚举时才需要雪花等分布式 ID。我在项目里也用了 UUID——但那是**分布式锁的 lockValue**（保证只有持锁者能解锁），业务主键保持自增。

**👨‍💻追问：分页深翻页性能问题（LIMIT 100000,20）怎么优化？**
> `LIMIT 大偏移` 需要扫描并丢弃前面 10 万行。优化：① 用 `游标分页`（基于索引的 `WHERE id > 上一页最大id ORDER BY id LIMIT 20`），跳过已翻过的行；② 子查询延迟关联。我列表用的是 createTime 排序，更深改进正用"索引 + 覆盖"优化。

## 七、Redis 缓存体系（重点）

### Q：你项目缓存三防具体怎么做的？

**话术：**
> 针对文章详情这个高频读热点：
> - **穿透**：布隆过滤器（1 万容量 / 1% 误判率）挡住不存在的 articleId，约 99% 无效请求拦在 Redis 前；误判的兜底用"空值缓存 NULL"60s TTL。
> - **击穿**：热点 key 过期瞬间大量请求回源。用 Redisson 分布式锁 + DCL 双重检查 + 自旋，保证**同一时刻只有一个请求**查库重建，其余拿克隆的值返回或兜底，DB 不被瞬间打爆。
> - **雪崩**：不同 key 的 TTL 加上随机抖动（我用 `ThreadLocalRandom` 生成），避免所有 key 同一刻集体失效。
> - **一致性**：Cache-Aside 模式，先更库后删缓存 + TTL 兜底；删除用 `SCAN` 而不是 `KEYS`（防阻塞 Redis 大库扫描）。

**👨‍💻追问：先删缓存还是先更库？为什么这么选？**
> 我用**先更库、后删缓存**（Cache-Aside 经典顺序）。若先删缓存再更库，更库期间另一个线程又读旧库写回缓存，就出现旧缓存。先更库后删缓存 + 合理 TTL，配合删除失败重试，能最大限度降低不一致窗口。严格一致性场景要上 binlog 订阅（Canal）或延迟双删，这里单体场景不需要。

**👨‍💻追问：删缓存失败怎么办？**
> 我封装了 CacheCleaner，删除操作加日志和重试，删除失败则依赖**TTL 兜底**（缓存本来会过期），不会永久脏。极端场景可引入 MQ 异步重试删除。

### Q：为什么用逻辑过期而不是物理过期？缓存重建为什么异步？

**话术：**
> 物理过期的痛点是：过期那一刻大量请求同时打 DB（击穿），虽用锁保证只一个回源，但**其他请求要阻塞等锁**，响应慢。逻辑过期是在 value 里塞一个"过期时间戳"做**软标记**：数据还在、标记过期时，**立即把旧值返回用户**，同时把"重建新缓存"的任务**丢进 cacheRebuildExecutor 异步执行**——用户不等、DB 不见锤、缓存不空窗。这里必须配线程池，因为重建任务不能丢也不能阻塞主请求。

**👨‍💻追问：逻辑过期多久触发一次重建？会不会频繁重建？**
> 我的逻辑过期时间较长（配合详情缓存 30 分钟 TTL），且重建时用分布式锁避免多个线程重复重建同一篇。异步重建失败会记日志 + 失效缓存，下次读取再触发，保证自愈。

## 八、Redisson 分布式锁

### Q：分布式锁怎么实现？为什么不用 setnx 命令自己写？

**话术：**
> 基础 setnx 自己写有三种坑：① 没设过期时间 → 持锁方宕机锁永不释放；② 设了过期但持锁逻辑执行超过过期时间 → 锁被自动释放，别的线程拿到锁，两个一起进临界区；③ 删除锁时可能误删——A 的锁过期后 B 拿到锁，A 执行完直接把 B 的锁删了。所以我用 Redisson 封装好的 RLock：
> - `tryLock(waitTime, leaseTime, unit)` 带**看门狗**自动续期（默认 30s，业务没跑完会续），避免业务超时长锁提前失效；
> - 解锁用**Lua 对比 value**（锁值 = 每线程唯一 UUID），只有持锁者能删，防止误删他人锁；
> - 分布式的本质是锁存在 Redis、所有实例共享，能跨多台服务器互斥。

**👨‍💻追问：看门狗续期机制原理？**
> Redisson 获取锁时若没指定 leaseTime，会给 key 设默认 30s 过期，并启动一个**后台看门狗线程**，每 10s（TTL/3）检查一次：只要业务线程还活着，就通过 Lua 把锁的过期时间重置回 30s，相当于"锁不会因业务超时而提前失效"。业务结束 finally 里 unlock 并取消看门狗。这解决了"锁过期时间设多长合适"的难题。

**👨‍💻追问：Redis 主从切换时空窗怎么办（锁丢失）？**
> 单节点 setnx/Redisson 默认在主从异步复制下有极端理论窗口：master 刚加锁未同步到 slave，master 挂了，slave 升级后锁丢失，可能俩客户端各持一把锁。严谨方案有两个：① Redisson 的**红锁 RedLock**（多节点过半加锁），但性能差、争议大；② 用 **ZooKeeper/etcd** 这类 CP 系统。我项目是单实例 Redis，能接受这极小概率，属于"根据业务容忍度取舍"。

## 九、RabbitMQ 消息队列

### Q：MQ 在你的项目里解决什么问题？为什么不用线程池直接异步？

**话术：**
> 主要解耦耗时/易失败的逻辑：AI 摘要生成、评论通知。选择 MQ 而非线程池，是因为线程池异步**没有持久化和确认机制**——进程崩溃任务就丢了。MQ 能：① **异步削峰**，把高并发的写平坦化；② **可靠性**，消息落盘、失败进死信队列重试；③ **解耦**，生产者不关心消费者是否在线。我配了 Jackson2JsonMessageConverter（禁止 Java 原生序列化，安全+跨语言），消息/队列/交换机**三重持久化**，并给业务队列绑定死信交换机。

**👨‍💻追问：怎么保证消息不丢？三个环节分别看。**
> 三条链路：
> - **生产者 → 交换机**：开启 `publisher-confirm`（confirm 回调确认送达）；
> - **交换机 → 队列**：开启 `publisher-return`（路由不进队列时回调）；
> - **消费者**：`acknowledge-mode=auto`（方法正常返回才 ACK），异常不重入原队列、进**死信队列**。
> 配合队列/交换机和消息的 durable 持久化，外加 broker 重启不丢。

**👨‍💻追问：消费失败重试机制？怎么防止重复消费？（[SummaryConsumer](file:///c:/Users/lenovo/Desktop/blog/blog/src/main/java/com/blog/blog/service/SummaryConsumer.java)里怎么做的）**
> 我在消费端做了"幂等 + 限流 + 死信"三层：
> ① **幂等**：先 `setIfAbsent(SUMMARY_DONE + articleId, 1, 24h)`，拿到才是第一次，拿不到说明已生成，直接跳过——防止 MQ 重投/重复消费导致 AI 多次付费调用。
> ② **限流**：调 DeepSeek 前用 RedisRateLimiter 令牌桶限流，超限就删掉幂等标记、抛异常让它进死信稍后重试。
> ③ **死信**：业务异常抛 `RuntimeException`，`default-requeue-rejected=false` 使消息进死信队列，配最大重试（max-retries=3），永久失败留死信便于排查。
> 数据更新的核心方法单独 `@Transactional` 隔离，避免把 DB 事务带到 MQ 监听长链路里。

## 十、多线程与线程池

### Q：项目里线程池配置和用途？参数为什么这么定？（[ExecutorConfig](file:///c:/Users/lenovo/Desktop/blog/blog/src/main/java/com/blog/blog/config/ExecutorConfig.java)）

**话术：**
> 两个线程池：
> - **cacheRebuildExecutor**（核心 5 / 最大 10 / 队列 200）：缓存逻辑过期时异步重建详情缓存，不阻塞请求、不丢任务。
> - **warmupExecutor**（核心 2 / 最大 4 / 队列 500）：启动时异步预热缓存，不阻塞应用启动。
> 两者都配 `CallerRunsPolicy`（队列满了由调用线程执行，**宁慢勿丢**）+ 优雅停机（`WaitForTasksToCompleteOnShutdown` + `AwaitTerminationSeconds`），避免线程泄漏。参数区分：cacheRebuild 请求频繁所以池稍大；warmup 只在启动跑一次所以池小、队列大吸收突发。

**👨‍💻追问：CallerRunsPolicy 是什么？跟 DiscardPolicy 区别？**
> CallerRunsPolicy：队列满 + 线程满时，不丢弃任务，而是把任务**交回提交任务的线程**同步执行——等于用"调用方速度"反向限流，保证任务不丢但会拖慢调用者（符合"宁可慢不丢"）。DiscardPolicy 直接静默丢弃（最危险，丢任务没察觉）。我选 CallerRuns 是因为缓存重建这种任务**不能丢**——丢了缓存就一直不重建，用户体验下降。

**👨‍💻追问：ThreadPoolExecutor 七大参数、执行流程、拒绝时机。**
> 七大参数：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler。
> 执行流程：① 核心线程未满 → 建核心线程执行；② 满 → 进 workQueue 排队；③ 队列满 → 建非核心线程执行；④ 非核心线程也满 → 触发拒绝策略（handler）。
> 拒绝时机是"线程达到 maximum + 队列已满"。核心线程默认不回收（除非 allowCoreThreadTimeOut），非核心空闲超 keepAliveTime 回收。

## 十一、布隆过滤器与限流

### Q：布隆过滤器原理？为什么能拦截 99%？

**话术：**
> 布隆过滤器是一个 redis bit 位数组 + k 个 hash 函数。写入时对元素算 k 个 hash 把 k 个 bit 置 1；查询时若**任一 bit 为 0 则一定不存在**，若全为 1 则"可能存在"（可能误判但不漏判）。所以它能**确定拒绝不存在**的 id。我项目用它拦截不存在的 articleId，误判的少数请求再走"空值缓存 NULL"兜底。参数我设 expectedInsertions=10000、falseProbability=0.01，按 1 万文章投建，启动时用 `findAllIds` 一次性加载已有文章 ID 初始化，文章数接近上限时触发扩容重建。

**👨‍💻追问：误判率怎么算？bit 位怎么定？**
> 误判率公式大致是 `(1 - e^(-kn/m))^k`，m 是位数组大小、n 是插入数、k 是 hash 个数。经验上 `m = -n·lnP / (ln2)^2`、`k = (m/n)·ln2`。我按 1 万/错误率 1% 反推出合适的位数组和 hash 数。扩容思路是**新建更大过滤器 → 批量重建 → 原子切换**，重建失败要回滚不能先删（避免空窗把有效请求也拦截掉）。

### Q：限流你会哪几种算法？项目用了哪些？

**话术：**
> 我项目用**令牌桶**（Redis Lua 原子实现，见 RedisRateLimiter）保护付费的 DeepSeek API（容量 5、每秒 3 令牌）。除此之外我理解市面上常见的：固定窗口（`ZINCRBY`/incr + 过期，边界有毛刺）、滑动窗口（`ZCOUNT`/`ZREMRANGEBYSCORE`，更平滑）、漏桶（恒定速率、不突发）。令牌桶优势是**允许一定突发**（桶容量吸收峰值）同时限制长期平均速率，最适合"控制成本 + 容忍短时峰值"的 AI 调用。微服务版还有 Sentinel（滑动窗口/QPS）和 Nginx `limit_req`（每 IP 10r/s）两层网关级限流。

## 十二、微服务架构（Nacos/Gateway/Feign/Sentinel）

### Q：微服务版架构？为什么拆这两个服务？

**话术：**
> 拆成 user-service（用户/认证）和 article-service（文章/评论/摘要），中间通过 Spring Cloud Gateway 网关做统一入口 + 路由 + 负载均衡，服务注册到 Nacos，跨服务用 OpenFeign 声明式调用（如文章服务查作者信息、判断评论删除权限），Sentinel 做接口限流熔断。
> 拆的依据是**业务边界和变化频率**：用户域稳定低频、文章域高频突变，分开后可以独立伸缩、独立部署、故障隔离。

**👨‍💻追问：Feign 调用失败怎么办？熔断降级怎么做？**
> Feign 默认配超时（连接/读取），失败可配 Sentinel 的 `@SentinelResource` + blockHandler 降级 + fallback 返回兜底值，网关层也可做全局熔断。拦截贴近业务：文章服务查不到用户时降级返回默认昵称，不让登录态崩溃。

### Q：分布式事务做了吗？跨服务改数据怎么办？

**话术：**
> 我拆的服务边界尽量**避免跨库强一致**：用户域和文章域各自独立，跨服务读用 Feign、写不跨库事务。真正的强一致场景我会讲 Seata（AT/TCC/Saga）原理，并强调**优先用最终一致性 + 消息补偿**而非全局事务。比如评论删除的权限校验，宁可读稍旧数据 + 幂等，也不引入分布式事务的复杂度。

## 十三、部署与运维

### Q：项目怎么部署的？讲讲你这套生产链路。

**话术：**
> 阿里云 ECS（香港）公网 IP 直连（未备案个人用），Docker Compose 编排 MySQL/Redis/RabbitMQ（只绑定 127.0.0.1 不暴露外网），应用用 systemd 的 blog.service 常驻（开机自启），Nginx 托管前端 dist + 反代 /api、/ws 并支持 WebSocket。安全组只开 22/80。密钥（DB 密码、JWT、DeepSeek key）通过 EnvironmentFile 注入，600 权限。

**👨‍💻追问：密钥怎么管理的？为什么用 EnvironmentFile 不用 systemd 硬编码？**
> 集中放在 /etc/blog/blog.env，chmod 600 root 所有。**遇到 key 变更不用动 systemd unit、不用改 docker-compose 重启容器**，改 env 后 restart 服务即可，集中管理 + 权限隔离。JWT 密钥用 `openssl rand -base64 48` 生成、生产环境覆盖默认值。API key 不落到代码和 systemd unit 里，避免误提交到 git。

**👨‍💻追问：重启云服务器后服务会自动恢复吗？踩过什么坑？**
> 会。docker（及 compose 容器）、nginx、blog 服务都 `systemctl enable` 了开机自启。踩过的坑：① blog 服务初始是 disabled，不 enable 实例重启后 Spring Boot 不会起来；② **节省停机模式**短期重启公网 IP 大概率复用，但官方不保证，IP 变了要同步改 Nginx server_name 和 CORS_ALLOWED_ORIGINS；③ Nginx 要能读 /opt/blog 目录，否则 Permission denied——给 /opt、/opt/blog 加执行权限。

# 附录：高频陷阱自检清单

面试官最爱用这几个"坑"钓你，提前背熟：

| 陷阱 | 你的正确回应 |
|------|------------|
| "你为什么不用 synchronized""怎么不用线程池异步搞定一切" | 区分**单机内存互斥 vs 分布式共享资源**，讲清边界 |
| "先删缓存还是先更库" | Cache-Aside：先更库后删缓存 + TTL 兜底 |
| "token 被偷了怎么踢" | 承认纯 JWT 无状态短板，用 Redis 禁用标记补救 |
| "锁过期了业务还没跑完" | Redisson 看门狗自动续期 |
| "删缓存失败" | 日志+重试+TTL 兜底，重依赖上 MQ/Canal |
| "MQ 消息丢了/重复消费" | 生产 confirm/return、消费 ack、幂等 setIfAbsent、死信重试 |
| "微服务事务一致" | 优先最终一致性 + 消息补偿，讲 Seata 原理 |
| "Redis 主从换锁丢失" | 单节点容忍 + 讲 RedLock/ZK 的取舍 |
| "为什么布隆过滤器你才设 1 万" | 给出 expectedInsertions/falseProbability 公式来源 |
| "JWT 存 localStorage 不安全" | 主动承认 + 框架转义 + 短过期 + Redis 封禁弥补 |

> 原则：**不会的不要硬编**。说"我理解它是…，在这个单体场景我用…规避了"，比 编一个看似高深的答案更稳——面试官更看重你**对取舍的理解**而不是背结论。
